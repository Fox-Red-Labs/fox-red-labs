Motor console

Not connected
Guard-
Not connected. Flash the normal image (with the bench guard), plug in the LaunchPad, and click Connect.

The safety guard is firmware on the board. It caps phase current, refuses a start outside the supply window or with the phase currents off zero, stops a run if this page goes quiet for 1 s, and caps run time.

The Hall table is not calibrated, so Start is off. Calibrate once (about 3 minutes, the motor turns slowly).

Connect to read the board. The lights are gray until they have a reading.

Use Chrome or Edge on a computer. This browser has no Web Serial.

Step prediction: the controller's ramp at the acceleration limit, with a band of 0.5 Hz plus 5 %. Nothing is fitted; the measured line is the page's own speed trace.

Settings

Start uses the speed slider; this is the exact way to set it, and the cap ends the run by itself. The speed slider changes a run live, these two do not.

Each value is read back from the board. A new value is written only when you click Apply, never while a run or calibration is under way. Ranges are the page's, not the firmware's. Restore writes back the values read at connect.

If the controller reportsCheck
DC bus over voltageThe supply is above the limit or the motor is pushing energy back. Read the bus on a meter and compare it with the page; the bench runs on 12 V.
DC bus under voltageThe supply sags under load. Check the adapter's rating and its lead, and watch the bus trace for a dip at the start.
motor over temperatureLet the motor cool, then clear the fault. If it returns cold, check what temperature input the firmware reads.
power module over temperatureThe driver is hot. Stop, let it cool, and check the phase current trace for a current you did not expect.
hardware over currentA phase current hit a hard limit. Look at the three phase traces for which phase went first, check the motor leads for a short, and run slower.
comparator over currentThe comparator tripped. Check the phase traces and the current limit reference before running again.
over loadThe shaft is loaded or held. Free it and run again.
motor lost phaseNo phase current: idle sense should sit near mid-scale on all three phases, and a held vector should read current on two. A phase that reads nothing points at a loose motor lead.
phase current unbalanceCurrent on the wrong phase: check which sense label is swapped by holding each vector in turn. Also check the three motor leads for a poor contact.
motor stallThe rotor did not follow. Free the shaft, calibrate the Hall table, and check the Hall states below.
startup failedThe start did not reach closed loop. Check that the Hall table is calibrated, that all six Hall states appear, and that the start current is enough for the motor.
over speedThe speed went past the controller's limit. Lower the reference.
estimator errorThe estimator reported a problem. Check the Hall states and the speed trace.
gate driver faultAt idle, this means the ILIMIT reference is not set: check the ILIMIT voltage before enabling the gates. Right at a hard acceleration, the DRV8376 H variant reports its cycle-by-cycle current limit on its fault pin: raise the limit or treat that report as a warning.
current offset checkThe current sense did not read zero at rest. Check the sense wiring and that nothing drives the motor while the page starts.
voltage offset checkThe voltage sense did not read zero at rest. Check the bus and phase sense wiring.

    Schemes
      About this page
      Connect an LP-AM13E230 with the DRV8376EVM from Chrome, watch the motor, calibrate the Hall table, run the Hall FOC firmware for a bounded time, and compare what each setting does. Speed in rpm is electrical Hz times 15 (4 pole pairs). Traces hold the last 10 s. The guard's phase-current trip defaults to 1.5 A; on this bench the handover to closed loop measured a transient of about 1 A, which tripped a lower setting. Change it under Settings, between 0.3 and 1.2 A, when no run is under way. One bounded 12 s run, unloaded, one motor, 12.4 V. The DRV8376 cycle-by-cycle current limit was off; with it on, its nFAULT report tripped the PWM at the handover. Four SDK faults are patched in the port, one of them (a Hall speed filter that diverges below about 38 kHz PWM) specific to running at 20 kHz. Speed was still settling and there was no load test. Later runs through the motor link do not hold this result: runs at 20 Hz fault more often than not, and a reversal and a speed step both fail.
      It is
      • It reads the Hall FOC firmware on the AM13E230 and DRV8376EVM live over the board's USB serial port and shows the motor in words and traces.
      • It calibrates the Hall table and runs the motor for a bounded time, under the bench guard in the firmware, and sets each stage's measurement beside what this bench measured.
      • It writes the controller's settings on your click, and keeps a table of the runs you make with the numbers computed in the page.
      • It talks to the board over the MotorVision serial protocol from the AM13 SDK, and writes only to firmware that carries the safety guard.
      It is not
      • Not a safety system. The guard that limits time, current and silence lives in the firmware. The page cannot add to it, and the Stop button is one more way to stop, not the only one.
      • Not a lab instrument. The run numbers come from the page's own sampling of the board's poll stream, not from a scope or a torque sensor. The page shows the update rate it got.
      Why Chrome or Edge?
      The page reads the board with Web Serial, which only Chrome and Edge on a computer offer. Safari and Firefox do not.
      Why does the board need the tab in front?
      While a run or a calibration is under way the page sends a heartbeat four times a second. The firmware stops the motor if nothing arrives for 1 s, and a hidden tab slows its timers.
      What does the page write without my click?
      Only the heartbeat, and only during a run or a calibration. Settings, the scheme and every start wait for a click, and settings are not written while a run is under way.
      What are the speed and current ripple numbers?
      Speed ripple is the peak to peak speed over its mean, over the 2 s before any step (or the last 2 s of a run with no step, leaving out its final 0.3 s while the speed falls), starting 1 s after the controller closes the loop. Current ripple is the same for the amplitude of the three phase currents, sqrt(2/3 (a squared + b squared + c squared)) at each sample. Both come from fresh updates only, so the update rate beside each run limits what they can see: under 20 updates in the window, there is no ripple. The three currents arrive one after another, so current ripple is reported only when they lie within 2 % of an electrical period; otherwise the run's note says so.
      How is the step response measured?
      Speed updates go through a 3-point median first, which removes a one-update spike. Rise is the time from 10 % to 90 % of the step (crossings interpolated between updates), overshoot is the peak above the final value as a share of the distance the speed travelled, and settling is the time from the step until the speed stays inside a band around the final value; the band is 2 % of the step, or twice the scatter of the final second where that is larger, at most 10 % of the step (the run's note says when). The final value is the mean of the last second. Where the signal cannot support a number, the cell is empty and the run's note says why: the speed did not end within 10 % of the commanded step, the updates are too slow to time the rise (it needs at least 4 across it), or the speed had not settled when the run ended.
      Why is the run to closed loop not the same as motor_start_ms?
      motor_start_ms is standstill to one shaft turn. The page has no shaft position, so it reports the guard's run time when the controller reaches closed loop, and the CSV says so in its note.
