One model, every kind of core

How it was measured

Room-occupancy CNN, 8.5k parameters, 157,824 multiply-accumulates (MACs) per inference, int8. Time is the fastest of 20 stored input windows, best of 5 calls each; plain C times include input quantization, NPU times are the model call only. Cycles per MAC is the clock cycles one inference takes, divided by its MACs; on an NPU chip it counts CPU clock cycles while the NPU works. Compilers differ by chip (TI Arm Clang, the C2000 compiler, GCC on the Cortex-A72 under Linux and on the comparison chips), so a row is one build, not the best the core can do. How it was measured

Flash and RAM are the model alone (weights, model code, NPU runtime) from each build's linker map, without the test program or stack; "not recorded" means no map was kept. Accuracy is the int8 model's, 4 classes, on 1,001 held-out windows on the Mac; on every board the chip gave the same class as the Mac on the 20 stored windows. Energy is EnergyTrace on the MSPM0 G5187 only: the loop's reading minus idle, median of 3, which says nothing about a product that sleeps between inferences.

The NPU beyond trained models

A fixed filter is a convolution layer, so the NPU runs it without training. On the MSPM0 G5187 at 80 MHz a 4-channel 64-tap FIR takes 0.566 ms against 16.8 ms for NNC's CPU code.

A window of 64 samples slides along the input; each output is the window times the taps, added up. The taps are the layer’s weights.

How it was measured

MSPM0 G5187, 80 MHz, 256-sample blocks, int8 in and out, median of 20 calls after a checked first call, one board, one flash per image. Energy, a streaming loop with overlap, and CPU work beside the NPU were not measured.

Fits the NPU well

  • Fixed FIR filters and filter banks

    The taps are the weights, so nothing is trained: 23.3 to 38.0x faster than NNC's CPU code, 16 of 16 images byte-exact against the integer reference.

    The run, the code

  • A detector in one graph

    Band filters, a max pool and a 1x1 comparator in one NPU graph, 49x faster than on the CPU.

    The run, the code

  • Keyword spotting

    The MLPerf Tiny DS-CNN with every compute layer on the NPU: 18.7 ms per inference, 91.0% on the 4,890 test clips.

    The run, the code

  • A wake word

    The wake-word example model on the NPU caught 120 of 120 synthetic phrases from 6 voices, fed over the serial port, not the board's microphone.

    The run, the code

  • Listening for an alarm pattern

    A small model on the NPU, fed by the onboard microphone, flagged a smoke-alarm pattern played from a laptop speaker.

    The run, the code

Does not fit, or gained little

  • A DFT as one fully connected layer

    Only 4.3x: the NPU does far less work per cycle on that layer shape.

    The run, the code

  • One channel

    Output channels come in fours, so against one hand-written C channel (3.29 ms) the 4-channel block (0.566 ms) gains only 5.8x.

    The run, the code

  • The 30k occupancy model

    One convolution stays on the CPU, so 2.3x instead of 3.8 to 21.6x for the smaller ones.

    The board FAQ

  • Re-scaling by exactly 1

    A 2^0 shift let the compiler drop a multiply and put the comparator back on the CPU; 2^-1 kept it on the NPU. A signed comparator sees positive peaks only.

    The run, the code

  • RAM, not speed, on the CPU side

    The CPU build of the same keyword model does not link in 32 kB of RAM, and ResNet-8 does not fit at all.

How to read this table, and what the numbers leave out

Why the same model differs. Time = clock cycles / clock. Cycles depend on the core, the compiler and the flash wait states (extra clock ticks the CPU waits for flash); this page does not isolate which of them causes the spread. Time came from each board's own cycle counter, mean of the 10 stored digits. The digit model's MAC count is not recorded here, so cycles per MAC cannot be given for it.

Reading the picture. 256 pixels go in, 10 scores come out, and the highest score is the answer. Compiler and instruction set differ by row: TI Arm Clang -O3 on the Arm chips, the TI C2000 compiler on the C28x (patched for its 16-bit char), GCC on the comparison chips.

Not measured with the digit model: AM13E230. It has an NPU; no digit-model build or run exists for them, so there is no digit number for the NPU. Flash is the whole image the linker built (model, test program, driver library; the CC13xx and CC23xx images include the SDK, so they are larger than the same model on an MSPM0), RAM as the linker placed it, with the stack the build reserved (the model keeps its working buffers on the stack; deepest use was measured only on the MSPM0G3507, 2,288 of 3 kB, and on the C28x, 1,596 of 2k words, not on the other chips), read from the map files; the C28x figure is quoted from the build notes, in 16-bit words doubled to bytes. AccuracyHow accurate edge AI models are, and why more parameters did not buy more.

More parameters did not buy accuracy. Int8 accuracy on 4 classes is 88.4 to 90.9% from 636 to 8.5k parameters, then falls to 85.4% at 33k while time on the MSPM0 G3507 grows 3.7x. The cause of the drop is not tested.

Port check: the same answers as the Mac

On every board, the 20 stored test vectors give the same class as onnxruntime, the Mac's model runtime, in NPU and CPU builds alike. This checks the port and says nothing about accuracy.

Accuracy on data the model did not train on

  • The figures above are int8 accuracy on 1,001 held-out windows, measured on the Mac. Int8 is the 8-bit integer form that runs on the chip.
  • Those windows were cut in 48-minute blocks from the same room and the same days as the training data, so near-duplicate conditions sit on both sides.
  • A stricter test holds out whole days: an 8k model trained once on the December days and scored on 1,983 January windows it never saw. Accuracy is 87.7%, but balanced accuracy is 40.2%. It called 159 of 170 three-person windows empty.
  • Read the same-day figure above as the optimistic one, and this day figure as what a new day in the same room gives.
  • Balanced accuracy is the average of how often each class is caught, so a model that calls everything empty scores low on it.
  • Why the drop: LP-MSPM0G5187 FAQ.

Live sensors

No board has run it on live sensors, and not all 1,001 windows on a board.

This is a judgment. It was not measured. 80 to 95% is fine when a wrong answer costs a minute, like a light or a screen. Near 100% is needed when a miss costs something, like a fault or fall alarm. Then watch the class you cannot afford to miss instead of overall accuracy.

How it was measured and the toolchainIntel Mac, 20 test vectors, best of 5; compilers differ by chip; NNC runs on Linux in GitHub Actions.

Four room-occupancy models (636 to 33k parameters, int8, from the model sweep) were built for every board where each linked. Every build that ran gave the same answers as the Mac on 20 test windows. Time is the fastest of 20 vectors, best of 5 per vector; NNC builds are medians of 3 runs, each after a fresh flash. The plain C timing also includes input quantization, so the NPU-against-plain-C gain is not like for like. Times are best case and cover the model call only: 3 runs agreed to the cycle, and the slowest of the 20 vectors ran up to 3.3% longer on the MSPM0 G5187 (the slowest-vector column of its results file). The NPU needs channel counts in multiples of 4, pooling kernels up to 4 and fully connected inputs of at least 16; a layer outside those limits falls back to the CPU. Measured 2026-10-05 to 2026-11-09 on an Intel Mac. Cycles = ms x clock. Flash and RAM come from each build's linker map: weights, model code and any NPU runtime, without the test program, driver library, C library, stack or the 20 test vectors. Compilers differ by chip (TI Arm Clang 4.0.4 or 5.1.1, the C2000 compiler 25.11.1, GCC on the NUCLEO); the build under each line is named in the chart tips and the table. Energy is EnergyTrace on the onboard probe, loop current minus idle current, 3 captures. 1 kB = 1,024 bytes.

A model goes from training to chip like this: train with TI Tensorlab (or PyTorch) with quantization-aware training, export to ONNX, then TI's Neural Network Compiler (NNC) turns it into C for the CPU or into NPU code, packaged as a library (mod.a) you link into a CCStudio project. NNC has no Intel Mac build, so it runs in a GitHub Actions job on Linux and download the library. That is why the NPU numbers here come from a fixed set of four models and not from any model you type in. Tensorlab 1.4 pins torch 2.11, which also keeps training off this Mac. TI lists hardware NPUs on more chips than are tested here (its device matrix includes the F28P55 and MSPM33C34, and its documents disagree about the F28P65). This page covers the two NPU chips that ran: the MSPM0 G5187 and the AM13E230. The LAUNCHXL-F28P65X rows are CPU only.

Results FAQ

Why do none of the four occupancy models fit the MSPM0 C1104?
The chip has 1 kB of RAM and the smallest model's buffers need 1.2 kB: the model's 1.1 kB plus 48 B for the test program. The build stops with a linker error. This is a link-only result from before the board arrived, for these models as built. The largest model's weights alone (33.6 kB) are also over its 16 kB of flash. Smaller models, such as the 1k digit model from BitNetMCU (an open-source tiny digit-recognising network), do link. Source: mspm0c1104/bench/prebuild-2026-10-08.md.
Why does the smallest model cost more cycles per MAC than the biggest?
A fixed cost per inference is suspected, such as quantizing the input and setting up each layer. It weighs more on 11k MACs than on 611k, but it was not isolated. Use the large-model figure for a large model; the explorer on the page shows the spread.
Is TI NNC faster than plain C?
On the C28x, yes: about twice as fast. On the Cortex-M0+ boards it depends on the model and the flags. NNC's code was built at -Os. On the MSPM0 G3507 it was 6 to 14% slower than plain C at -Os on the three smaller models and faster on the largest. Plain C at -O3 beat it on every model. The G3507's plain C -Os figure for the largest model is 26.1 cycles per MAC, against 20.2 for the next size down. That runs against every other board's trend and is a single run, so it needs a rerun. No NNC build at -O3 was made.
Why does the 33k-parameter model not fit the MSPM0 L1306?
Its activation buffers alone need 4.1 kB and the chip has 4 kB of RAM, so the build stops with a linker error. The three smaller models run on it.
Why do some LAUNCHXL-F2800137 RAM builds say No: RAM when the same model runs?
Running from RAM avoids flash wait states, so each model was also built with its code and data in RAM. For plain C, the 33k-parameter model's weights are 65.7 kB against 36 kB of RAM. The 8.5k-parameter build also carries 10.2 kB of test vectors. The linker said `program will not fit into available memory` (c2000-launchpad/bench/edgeai/build-occ_cnn_8k-4-RAM/build.log). The NNC 8.5k-parameter RAM build is over the RAM even without the test vectors. That rests on an estimate of 38.8 kB of flash content plus 9.2 kB of RAM, not built to the end. Run them from flash, as the flash rows do.
How much faster is the Cortex-M33 chip than the Cortex-M0+ chip at 48 MHz?
2.4 to 3.0 times, by model size, in the measured rows: plain C at -O3 on the CC1354P10-1 (M33) against the CC2340R5 (M0+). The two differ in core, flash system and compiler build, so the ratio is not the core alone. Flash wait states are the suspected part of the gap. The same build was not run on both.
What does floating point cost on a chip with no FPU?
A 256-point FFT took 10.9 times the cycles in 32-bit float than in q15 on the CC2340R5 (no FPU) and 1.4 times on the CC1354P10-1 (FPU). The occupancy models are int8, so they avoid that cost.
Why does the measured 176 ms for TI's motor bearing fault example differ from TI's published 229.01 ms?
TI's example ran as shipped on the MSPM0 G3507 at 80 MHz, one run. One run, reason not found. Compiler version, flags or clock setup are possible, but this was not checked.
Why is the MSPM0 G3507 waveform classifier (hello_world_ai) timed at 32 MHz?
That row ran at the example's own 32 MHz setting. The other MSPM0 G3507 rows ran at 80 MHz, so the times are not comparable. The data records the clock but not why the example uses 32 MHz.
What does the linker message look like?
On the LAUNCHXL-F2800137 the linker printed program will not fit into available memory (c2000-launchpad/bench/edgeai/build-occ_cnn_8k-4-RAM/build.log). For the Arm chips the table records the sizes, not the message.
Where are the NPU numbers?
In the section on the NPU against the CPU, higher on this page, and as NPU dots in the explorer. A board with no row has no estimate.

Five words this page uses
  • Inference: one run of the model on one input, here one digit or one sensor window.
  • MAC: a multiply-add, the basic step of a neural network.
  • int8: weights stored as 8-bit integers instead of floats, so the model is smaller and faster.
  • NPU: a hardware block that does many MACs at once, beside the CPU.
  • NNC: TI's Neural Network Compiler, which turns a trained model into C for the CPU or code for the NPU.
