All demos for this board

    Digital Lab: program and test a TI LaunchPad in your browser

    Pick any board, even one you do not own, and see an example run inside its chip. With a board connected you also get its pins, a map of its registers and its serial output. It is not a source debugger: no breakpoints or stepping. Tested on a Mac in Chrome (November 2026); Windows has not been tried yet.

    What it does, and what it does not

    What it does: saves the board's flash, writes a demo through the board's debug probe, starts it and checks the result (an LED pin, values in the chip's memory, or its serial output), then puts the saved copy back when you ask. It is not a source debugger: no breakpoints, stepping, or register and memory views. For those, use CCStudio, or GDB with OpenOCD from the terminal route below.

    Open this page in Chrome or Edge. Chrome and Edge on a computer, and Chrome on an Android phone, can talk to a board over USB.

      Why only these?
        
      A web page may list only the boards you have already allowed on this site: that is all the browser lets it see. A board you plugged in but never chose appears after you press Connect and pick it once, and then stays on this list. This page can read only an XDS110 debug probe, so a board with another kind of USB port does not show. A probe that CCStudio, UniFlash or another tab holds shows as not checked until that program lets go.
      
    
      
    
      
    
      Plug the board in with its USB cable. Chrome lists it as XDS110: pick it.
      
    
      Before you connect: Mac, Windows, Linux, Chromebook, and what can block it
      
      Mac: Chrome or Edge, nothing to install.
      
      
      Windows (not tried yet): Chrome or Edge; the XDS110 needs no driver for this page. If the list stays empty, unplug the board and plug it in again; Windows installs its own USB driver the first time.
      
      
      Linux: Chrome or Edge, plus two udev rules so your user may open the probe (in the table at the bottom). Without them Chrome lists the board but cannot open it.
      
      
      Chromebook and school PCs: works when the administrator allows this site to use USB devices (the WebHID and Serial device policies).
      
      
      Not here: Safari, Firefox and iPhone cannot talk to the board; Chrome on an Android phone can, with an OTG adapter. The page must be on https or localhost.
      
      
      Chrome's list is empty: use a USB cable that carries data (many are charge-only), plug it into the board's debug USB port, and check the board's power LED is on. Press Connect again.
      
      
      Board or port busy: close CCStudio, UniFlash, any terminal program and other browser tabs that hold the probe, then unplug the board, plug it in and press Connect.
      
      
      Blocked by the browser: open chrome://policy and look for rules that turn off WebHID, WebUSB or Web Serial. A work or school administrator sets those.
      
      
      Probe firmware too old: update the XDS110 firmware with TI's xdsdfu, then press Connect.

    Put back what was there
    
            On the LaunchPad kits this page programs over the debugger (the MSPM0 and MSPM33 boards), it saves the board's flash to your Downloads folder as a .json file before it first writes. Choose that file to put it back; it goes back only onto the chip it came from. The CC23 and CC27 Bluetooth boards save .bin files instead, which this page cannot put back: connect one to see its steps.

    If something goes wrong
    
              
    
              You seeDo this
              
    
              What do Works, Should work and Could work mean on an example card?Works: ran on this board. Should work: it ran on a sister board with the same chip family. Could work: not run on a board yet. Not for this chip: it does not fit. The LP-MSPM0G3507 examples say Should work because they ran from the terminal and no run from this page is recorded yet.
              
    
              The Registers tab says "Not connected"Registers need a board plugged in. The tab lists where each block sits in the chip (from the chip's header file); this page does not read their values. Inside the chip reads a running board's blocks without stopping it.
              
    
              Why can I not run an example on a board I picked from the list?The list lets you look at any board without owning it: you see its examples and, where one is drawn, the chip view. Running one needs that board plugged in and connected with the button at the top. Nothing is written to a board until you press the write button.
              
    
              Safari, Firefox or an iPhone shows "Open this page in Chrome or Edge."Those browsers cannot talk to a board over USB. Use Chrome or Edge on a computer, or Chrome on an Android phone.
              
    
              Garbled characters in the serial outputThe serial speed (baud rate) does not match. The demos use 115200 baud, 8N1. The demo's steps name the speed (baud rate); set the same one on the port.
              
    
              Is it safe to try, and what does the page save?Before it first writes to an MSPM0 or MSPM33 LaunchPad, the page saves the board's flash to your Downloads folder as a .json file. Open "Put back what was there" to choose that file and restore it. CC23 and CC27 boards save .bin files that this page cannot put back.
              
    
              The device list is emptyUse a cable that carries data, in the board's debugger connector, straight into the computer. A charge-only cable, or CCStudio or UniFlash holding the probe, looks the same.
              
    
              "… is not on an LP-…" or "… reports DEVICEID …"That XDS110 belongs to another board; nothing was written. Connect again and pick another.
              
    
              "the chip's debug port did not power up"The program may be in a deep sleep. Hold S1, press and release S3, keep S1 held two more seconds, then try again at once.
              
    
              The check says the LED did not do what you askedCheck the LED's jumpers are on, as shipped, and send it again.
              
    
              No message arrivesCheck the UART jumpers are on XDS (as shipped), and that you picked the serial port named in the steps.
              
    
              The board will not connect at all, even after unplugging itThe chip may be locked by a program that went wrong. This page cannot recover it. TI's MSPM0 chips have a mass erase through the debugger (UniFlash, or the terminal route in Go further): it erases everything on the chip, including its boot settings, so use it only as a last step.
              
    
              Two boards plugged in, both called XDS110Pick either. The page reads the chip, names the board, and lists every board it can see under Connect, each with a Use this one button.
              
    
              The board's program restarted when I connectedExpected, once: if the chip does not answer, the page restarts it to wake it. Nothing is written until you press the button.
              
    
              An Android phoneChrome on Android, and a cable from the phone's USB-C port to the board's USB port. The page uses WebUSB there; it passed through that interface from a Mac but has not been run on a phone yet. The two recipes that read the board's serial port need a computer.
              
    
              WindowsTested on a Mac in Chrome. Windows has not been tried yet. Close CCStudio and UniFlash first: they hold the probe.
              
    
              Linux: no device, or permission deniedNot tried yet. Chrome reaches the probe through hidraw, and the serial port through ttyACM, so two rules go in /etc/udev/rules.d/70-xds110.rules: KERNEL=="hidraw*", ATTRS{idVendor}=="0451", ATTRS{idProduct}=="bef3", TAG+="uaccess" and SUBSYSTEM=="usb", ATTRS{idVendor}=="0451", ATTRS{idProduct}=="bef3", TAG+="uaccess". Then run sudo udevadm control --reload-rules && sudo udevadm trigger and replug. OpenOCD and the serial port also need your user in the dialout (or uucp) group.
              
    
              Connect shows no device at all, on a managed Chromebook or PCThe administrator's device policy blocks it. The two policy lines IT needs are WebHidAllowDevicesForUrls and SerialAllowUsbDevicesForUrls, with vendor 1105 and product 48883, for this site.
              
    
              A CC23 or CC27 board stopped while the light program was being writtenThe board may hold a partly written program. This page cannot put the saved .bin files back: follow that board's steps under "Put back what was there" (TI's UniFlash), or press the button again to write the light program whole.
              
    
              "the debugger stopped answering"Unplug the board, plug it back in, reload this page and try again.
              
    
              "The board was unplugged or lost its USB link while the page was writing it"The board may hold a partly written program. Plug the USB cable back in, press Connect, then use “Put back what was there” with the .json copy the page saved before the write. Do not run a demo until Put back says it is done. If the cable comes out again, press Put it back again: it compares first and writes only what still differs. If the page says no copy was saved, run the same demo again instead.
              
    
              "The browser could not open the board" (Chrome: "Failed to open the device.")Another program holds the probe: close CCStudio, UniFlash, terminal programs and other tabs, then replug. On Linux, install the two udev rules in the Linux row.
              
    
              Any other failurePress "Download a diagnostic record" and attach the file to your report. It lists what the page tried and how each step ended, with no flash contents, Wi-Fi names or passwords, addresses or full probe serial numbers. Open it before you send it.
