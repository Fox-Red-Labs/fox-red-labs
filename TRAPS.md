# Traps that repeat across TI LaunchPad development kits, with the exact error text and the fix

Six rules keep a board recoverable: pick the probe by serial number, never touch the boot configuration area, back up flash before the first write, and check pins, stack and RAM before flashing. The table below matches the exact error text of the traps seen on two or more boards.

**How to use this file.** Read it first, then the board's own `AGENTS.md`, which has the pins, memory sizes and traps that belong to that one board. Where the two disagree, the board file wins.

## Before you touch the board

1. **Name the probe by serial number when more than one board is on USB.** Tools pick one without saying which, and some LaunchPad kits share one serial (`xdsdfu -e` lists them).
2. **Never write or erase the boot configuration area.** It is NONMAIN on MSPM0 and MSPM33, CCFG and SCFG on CC23xx and CC27xx; a wrong value locks the debug port.
3. **Back up flash before the first write.** `python3 tools/frl/frl.py backup --board <board> --probe <serial>` reads every region twice, compares them and keeps the copy; where a board has no recipe there, its `AGENTS.md` says how. Restore everything except the boot configuration.
4. **Do not erase all of main flash "to start clean".** The programmer erases what it needs; a blank chip can hold the debugger off.
5. **After changing the device in SysConfig, recheck every pin and the clock.** The old board's pins and clock settings stay with no warning.
6. **Set the stack size yourself and read RAM use from the linker map before flashing.** Small chips have no memory protection, so an overflow corrupts data silently.

## If you see this

| What you see | What it means | Do this | Check |
|---|---|---|---|
| `A firmware update is required for the XDS110 probe` (sometimes then `Failed: Timed out after 45 seconds` or error -264) | Probe firmware is older than 3.0.0.43. On some probes it only warns | If the command still flashes, carry on. If it fails, run `xdsdfu -I <serial> -m`, then `xdsdfu -I 00000000 -f firmware_3.0.0.43.bin -s <serial> -r` from CCStudio's `ccs_base/common/uscif/xds110/` folder | `xdsdfu -e` shows 3.0.0.43 |
| `Error: checksum mismatch - attempting binary compare` or `Unidentified PART[0x1508]/variant[0x16], unknown DeviceID[0xbba9]. Attempting to proceed as mspm0x.` | OpenOCD messages that look like errors. The first is a quick check that falls back to a read-back; the second is a missing table entry | Read the next lines. Treat `** Verified OK **` as the result. After `** Verify Failed **`, run the same command again | `** Verified OK **` is printed |
| `Could not find MEM-AP to control the core` (after `Unable to reset target`, or with `Peripheral mis-configuration (e.g improper watchdog or clock)`) | Blank main flash or a reset loop: the boot ROM keeps the debugger off the CPU | On MSPM0: `mspm0_mass_erase`, then `flash write_image erase <file>.out 0x0 bin` with no reset, then `mspm0_board_reset`. On MSPM0L1306, hold S1 while pressing S3 to enter the bootloader if there is no terminal | A new connect finds the CPU |
| `Device Connection Error. This could be caused by the device having gone to low power mode ... try 1) Invoking BSL, 2) Calling a DSSM Mass erase` on MSPM33, and a reset or replug does not clear it | The image in main flash faults at boot (often a write that was cut off), so the CPU never stops for the debugger | Before any DSSM erase, connect with the flash setting `EnableWaitForDebug` on (CCStudio scripting `settings.set`), which holds the core in its reset handler; then reflash main only. The board's `AGENTS.md` has the steps | The core halts at its reset vector and the reflash verifies |
| A flash write passes verify (an on-chip check and a read-back) on the MSPM33 or AM13, but the new program never starts: the LED does not change, or the old program still runs | A program that switched the flash caches on (TI's examples do at 160 MHz) leaves old flash lines in them. The debugger reads flash past the caches, so verify passes, and the reset then fetches the old vector table from the cache. Seen 2026-10-22: PC inside the previous image after a correct write | Clear `FRI FRD_INTF_CTRL` (0x4002900C: bit 1 data cache, bit 2 code cache; same address on both chips) while the core is halted, write, then reset. The Digital Lab does it | The LED toggles at the image's rate after the reset |
| MSPM33 or AM13 does not answer the debugger after an interrupted write or an erased vector table, and a reset or replug does not clear it | The boot code faults before the debugger can stop the core (CFG-AP `BOOTDIAG` reads 0x08000007) | Wait-for-debug with the register sequence CCStudio's debug server writes, taken from its own log: ten times (SPREC bit 0, DPREC0 bit 14, SPREC bit 0) at AP 4, then DPREC0 0x002C4027, 0x000C6027, 0x000C602F, DHCSR halt requests with DEMCR VC_CORERESET set, DPREC0 0x000C202F, 0x0048202F, 0x0008602F, 0x00120008. The GEL file's shorter hold-then-0x00120008 is not enough on a chip that faults at boot. The Digital Lab connects this way first; nothing is written and no mass erase is needed | The core halts at its first instruction and flash reads back |
| `Unknown Device ID[0x0], cannot identify target` and `auto_probe failed` | OpenOCD read zeros from the chip's state after a program ran | Load any image with `dslite.sh --mode flash`, then use OpenOCD again | OpenOCD names the device |
| `Error -260 ... An attempt to connect to the XDS110 failed` while `xdsdfu -e` lists the board | Another process holds the debug server, often a parallel flash | Run the command again, up to six tries a few seconds apart. Do not kill a DSLite process you did not start | The retry connects |
| `Error -615` or `The target failed to see a correctly formatted SWD header` | Probe not seated, board unpowered, or a hand-written connection file with the wrong SWD setting | Press the probe firmly onto the debug pins and replug USB. Use a `.ccxml` written by CCStudio or shipped by TI and add only the probe serial. Remove an `SWD Mode` property copied from a Cortex-M33 board | Flash connects |
| `Failed: An invalid processor ID has been found.` or `Error -2131 @ 0x0 Unable to access device register` | The connection file was not made for this exact chip, or the chip side is powered from outside | Copy TI's file for the exact device and add the probe serial. For -2131 on F2800137 set `SWD Mode Settings` to 4. Flash before wiring outside power | Probe identify succeeds |
| `Error -242 @ 0x0 A router subpath could not be accessed` | A sleeping program holds the only debug connection. The chip connects only in the first seconds after power-on | Start a loop of loads, then replug USB, or cut power from a switchable hub port (off 6 s) and load at once | One load goes through |
| `Debug is not allowed based on`, `Unable to authenticate with Secure Debug Manager!`, `Error -2001` | CC27xx: a chip erase cleared CCFG and SCFG, so the debug port stays closed | Recover over SACI with `cc2755p10/recovery/saci_program.js` (run `check` first; the board's `AGENTS.md` has the steps). Do not erase again | Debug connects after reset |
| Serial port silent, or one odd character | Wrong baud for the image on the board, port opened after the program printed, or the wrong port | Open the port first, set the baud in the same program, use the port ending in 1. Baud is 115200 for SDK examples, 921600 for some images | Text appears at that rate |
| `ERROR! Must execute for at least 10 secs` | The cycle counter reads 0 (`DWT->CYCCNT`, or SysTick on MSPM0C1104) or the run is too short or wraps | Time with a free-running timer or the RTOS tick. Choose iterations so a run lasts 10 to 26 s | Score prints |
| `error: program will not fit into available memory` (for example `.bss` size 0x8b0) or a stack pointer near `0x1FFFFE18` | Image larger than RAM, or the stack ran below the start of RAM | Read the map first. Build for flash if RAM is too small. Paint the stack with a pattern and set `--stack_size` | The paint pattern is intact below the stack's low-water mark |
| Zephyr image fills RAM and stops at `***** HARD FAULT *****`, or prints nothing | The C library heap arena is sized wrong for a small chip | Set `CONFIG_COMMON_LIBC_MALLOC_ARENA_SIZE=0` if the program never calls `malloc`, or a small value such as 1024 or 2048 if Bluetooth needs it | Boot log appears |
| `make` stops at once, `sysconfig_cli.sh: not found`, or SysConfig cannot find a product | The SDK `imports.mak` names folders a Mac does not have | Pass the SDK folder, `SYSCONFIG_TOOL` and `TICLANG_ARMCOMPILER` on the command line, with `GCC_ARMCOMPILER=` empty | The `.out` file exists |
| `.bin` file of 1.22 GB, or `Values at address 0x4E020750 do not match (expected: 0x00, actual: 0xFF)` | A raw binary from address 0 spans to the boot configuration at 0x4E020000. In `dslite.sh`, `-e` is verbose, not erase | Flash the `.hex` or `.out`. Leave `-v` off on CC23xx | Flash finishes in seconds |
| Builds and flashes, but the LED stays dark | The example toggles another board's pin. A SysConfig device change keeps it | Set the LED pin by hand from the board's pin table | A pin read shows toggling |
| An interrupt handler never runs, no error | The interrupt line does not exist on this chip, or a macro keeps its name and changes its value | Check the number in this chip's header and vector table | Handler counter rises |
| Builds fail with `ENOSPC` | CCStudio and DSLite each write a 0.6 to 1.4 GB cache under `~/.ti/ccs2101/<n>/<m>/` | Run `lsof +D ~/.ti/ccs2101`. Delete only slots with no live lock. Turn off VS Code's C/C++ indexer for repos that link into TI folders | `df -h` shows free space |
| A console that echoes the Wi-Fi password you type (CC35X1 OTA example) | The board prints every typed character back, so a log or screen capture holds the password | Mute the echo until the next line break in any page or script that drives it; never save the raw log | The saved log has no password |
| `xdsdfu -e` lists no probe, and the LaunchPad has no USB port | LP-EM boards need a separate LP-XDS110 or LP-XDS110ET, and some also need a second cable | Clip the probe on, set its target-power jumper as the board's file says (XDS or EXT), replug | A probe serial is listed |

## Numbers that mean something is wrong

- Some UART rates above 3 Mbaud send nothing, with no error (divisor 0). Test the exact rate.
- CoreMark per MHz is near 2.3 to 2.4 on Cortex-M0+ and 4.2 to 4.5 on Cortex-M33 at a low clock. Far below it means wrong flags or flash wait states.
- A blink build takes 3 to 6 s on MSPM0 and OpenOCD flashes in under a second. Minutes mean the wrong probe, or a tool waiting for an answer.
