# How do you build Zephyr for the TI TMDS62LEVM (AM62L): DDR, SRAM and core 1 images?

Six Zephyr hello-world images build with `setup.sh` on an arm64 Mac (2026-10-18). The SRAM image runs on the board over JTAG, and an image on core 1 runs beside Linux. The build lives in a 16 GB sparse-bundle disk image mounted at `/Volumes/zephyr` (workspace `zephyr-am62l`, tools `zephyr-toolchain`), because Zephyr's Kconfig step cannot take a space in the path and a symlink does not help (west resolves the real path). After a reboot of the build host: `hdiutil attach <path>/zephyr.sparsebundle`.

Terms: [docs/vocab.md](../../docs/vocab.md). **SRAM** is the 160 kB of memory on the chip, **DDR** the 2 GB LPDDR4 beside it, **TF-A** is Arm's secure-world firmware, **PSCI** starts and stops CPU cores, **DSLite** is TI's command-line debug server. 1 kB = 1,024 bytes (KB below means the same).
 Pinned: upstream Zephyr at commit a915b2f (the `am62l_evm` board with OSPI, SCMI and PWM; no release carries all of it), the aarch64 compiler from Zephyr SDK 0.17.4, west 1.5.0, CMake 4.4.4, ninja 1.13.2, uv 0.13.1. Every download is checksummed. About 3 GB of disk the first time.

| Image | What it is | Memory | Firmware under it | Start | Result (2026-10-18, hello world) |
|---|---|---|---|---|---|
| `build-ddr` | Upstream board file as is | LPDDR4 at 0x82000000 | TF-A and TIFS (SCMI clocks and power, PSCI for core 1) | U-Boot: `fatload mmc 1:1 0x82000000 zephyr.bin; dcache flush; icache flush; dcache off; icache off; go 0x82000000` | links: 74.0 kB code, 5.4 kB data, 4.1 MB bss (4.0 MB is `k_mem_page_frames`, the kernel's page bookkeeping for 2 GB); `zephyr.bin` 77.5 kB |
| `build-sram-all` | `sram-all.overlay` plus `bare-el3.conf` (8 translation tables) | WKUP plus MAIN SRAM, 144 KB from 0x707F0000 | none: one core at EL3, no SCMI, no PSCI | JTAG load (DSLite, CCStudio's `AM62L_SK_EVM` board file) with the DDR never initialized; later the boot ROM's phase-1 payload (builds; not run on the board) | links: 124 KB of 144 (20 KB spare); with 6 tables it was 116 KB and panicked in Renode at the pin-control mapping. **Boots and prints in Renode. Works on the board:** prints over UART A, 2026-10-21 (JTAG load, DDR never initialized; `docs/experiments/2026-10-21-am62l-sram-zephyr.md`) |
| `build-sram-all-tight` | plus `bare-el3-tight.conf` (4 translation tables, 1 to 2 KB stacks) | same | none | same | links: 120 KB of 144 (24 KB spare) |
| `build-sram-main` | `sram-main.overlay` plus `bare-el3.conf` | MAIN SRAM only, 80 KB at 0x70800000 | none | same | does not link: 44 KB over |
| `build-sram-main-tight` | plus `bare-el3-tight.conf` | same | none | same | does not link: 40 KB over |
| `build-sram-main-floor` | plus `floor.conf` (no C-library heap) | same | none | same | does not link: 24 KB over. The floor for a Zephyr hello world on this chip, with the 8 tables it needs, is 104 KB |

Where the RAM goes (`nm --size-sort` on `build-sram-all`): translation tables 32 KB at 8 tables (4 KB each; 6 is too few, Renode showed), the C library's malloc arena 16 KB, the main, idle and interrupt stacks 4 KB each, two thread objects of 816 bytes. The 49 KB of code is the kernel, the MMU and GIC setup, the 16550 UART driver and printk; nothing in it belongs to the sample. Reading: the 80 KB safe map is 24 KB short even with every cut; the 144 KB map is the DDR-less map on this chip.

`setup.sh` builds the first, second and fourth from nothing; `rebuild_sram.sh` on the build host rebuilds the SRAM images from the overlays in a minute; the tight and floor builds were `west build` with `-DEXTRA_CONF_FILE="bare-el3.conf;bare-el3-tight.conf[;floor.conf]"`.

Why these images: the AM62L's ROM and Linux both want the on-chip SRAM, so a DDR-less Zephyr needs its own map. The SRAM map and what each overlay assumes are in the overlay comments. A build that overflows its region is a result (the number is the finding), not a stop.

The board has no `west flash` path (Zephyr's docs load it from U-Boot or debug it with OpenOCD newer than 0.12.0). Run `setup.sh` on any Mac or Linux machine with 3 GB free; `ZP` and `TC` move the folders, `APP` builds another application (`APP=samples/subsys/shell/shell_module`).

## Before the board: the SRAM image in Renode

`renode/am62l-sram.repl` is the AM62L as Renode sees it, made by Antmicro's `dts2repl` from the `build-sram-all` device tree: a Cortex-A53, GICv3 at the chip's addresses, the 16550 UART0 at 0x02800000 with the K3 4-byte register stride, the 144 KB SRAM span, the NOR window and the DDR. Everything else is a tag (reads 0, writes logged): no clock tree, no ROM, no TIFS, no timing. `renode/run.sh` boots the image for three simulated seconds and prints the UART capture. What it proves: EL3 entry, the MMU with the chosen table count, the GIC, the UART driver and the memory map. What it cannot: whether UART0 has a clock without TIFS, whether the ROM accepts the image, any speed or power number. Renode on an arm64 Mac build host: `brew install renode/tap/renode` (trust the tap first: `brew trust renode/tap`).

## Zephyr on core 1 beside Linux (2026-10-22)

`rebuild_core1.sh` (on the build host) builds three images of `apps/core1-hello` with `patches/gic-skip-distributor.patch` applied to the workspace (`git apply`, adds `CONFIG_GIC_SKIP_DISTRIBUTOR`): `build-sram-core1-uart1` (A, console UART1, 49.2 kB code, 124 of 144 kB), `build-sram-core1-ring` (B, console in the 4 KB SRAM ring at 0x70813000, 116 of 140 kB) and `build-sram-core1-xip` (C, code run in place from WKUP SRAM, data from 0x70801000 so the SCMI mailbox page at 0x70800000 is never written; 43.7 kB code, 6 translation tables). A and B overlap Linux's SCMI mailbox, so only C and D are for use beside Linux. Image D (`build-sram-core1-el1`, added after the debugger failed to attach to a powered-down core 1, DSLite error -1062) is C's map built with `core1-ns.conf` (non-secure, no EL3 path, no PSCI or SCMI code): 43.7 kB text and data, 60 kB bss; `zephyr.bin` 43.7 kB; entry 0x707F10BC; meant to be started by Linux through `am62l-evm/linux/cpu1_start/` (that module is not compiled). `ONLY=el1 rebuild_core1.sh` builds it; `renode/run-ring-el.sh` runs it at EL1 (`EL=2` for EL2) and decodes the ring (banner and ticks, 2026-10-22). `renode/run-ring.sh` runs B or C and decodes the ring; `../tools/ringcat.py` reads the ring on the board.

**Image E, the one that ran (2026-10-22).** `build-ddr-core1` (`core1-ddr.overlay` plus `core1-ddr.conf`, `apps/core1-hello`, the distributor-skip patch): linked at 0xE0000000 in a 256 MB DDR region, entry 0xE00008BC, `zephyr.bin` 44.0 kB (sha256 6543a9a3fa6233850a789302c08976b47ac75688649a8705d74d8a9073dc0778), no PSCI, SCMI or SMC code, console a 4 KB ring at 0xEFFFF000. Started from U-Boot by `am62l-evm/tools/psci_stub.py` (`CPU_ON`, MPIDR 0x1) at non-secure EL1; read from Linux (`maxcpus=1 mem=1536M cpuidle.off=1`) through `/dev/mem`. SRAM images C and D were not used because Linux and TF-A occupy that SRAM. Result: works; `docs/experiments/2026-10-22-am62l-linux-zephyr-amp.md`.
