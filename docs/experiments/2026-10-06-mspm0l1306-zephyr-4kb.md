# Can Zephyr run on the TI LP-MSPM0L1306, a chip with 4 kB of RAM and no Zephyr board?

**Short answer.** Yes. With a board file written for this repo, a corrected copy of Zephyr's GPIO driver, the UART pins written into the devicetree by hand and one heap setting, hello_world, blinky and a standard 2 kB CoreMark run on the board. CoreMark scores 59.70 per second at 32 MHz (1.87 per MHz) with 16 bytes of RAM left. Most of Zephyr's other samples need 6 to 17 kB of RAM and do not link.

Terms: [vocab](../vocab.md) (Zephyr, devicetree, pin-mux, stack, heap, linker). Errors and fixes: [LP-MSPM0L1306 FAQ](../../mspm0l1306/FAQ.md). 1 kB = 1,024 bytes.

**Question.** Zephyr 4.4.2 lists the MSPM0L1306 chip but has no board for its LaunchPad. Can a builder still use Zephyr on it, and does anything useful fit in 4 kB?

**Vendor position.** Zephyr's tree (4.4.2, read 2026-10-06) has the chip (`soc/ti/mspm0/mspm0l`, `dts/arm/ti/mspm0/l/mspm0l1306.dtsi`) and boards for the LP-MSPM0G3507, LP-MSPM0G3519 and LP-MSPM0L2228, not this one. TI's MSPM0 SDK documents no Zephyr path for it. No upstream request or pull request was found for an `lp_mspm0l1306` board.

**What was tried.** Intel Mac, macOS 15.7.9, Zephyr 4.4.2, GCC 12.2.0 (Zephyr SDK 0.17.4), xPack OpenOCD 0.12.0+dev, probe serial <probe serial>. A board folder copied from the LP-MSPM0L2228 and LP-MSPM0G3507 boards, with this kit's pins from TI's board notes and SDK: `mspm0l1306/zephyr/boards/ti/lp_mspm0l1306/`. Built with `-DBOARD_ROOT`, flashed with OpenOCD, read on the serial port. Then the project's Zephyr benchmark, fitted to 4 kB (`mspm0l1306/zephyr/mcu-bench-l1306/`). Commands: `mspm0l1306/zephyr/build.sh <target>`.

**How far it got.**

- Configure and compile: blinky failed, `error: 'IOMUX_PINCM38' undeclared here (not in a function)`. Zephyr's GPIO driver has the pin table of the 80-pin L222x, not this 32-pin chip. Fixed with a corrected copy of the driver in the board folder.
- There is no pin-mux file for the L130x family; the two UART pins were written into the board's devicetree by hand.
- Link: hello_world 3.7 kB of RAM (264 left), blinky 3.8 kB. The benchmark as written for the G3507 overflowed by 8.5 kB; it fits after smaller stacks, buffers moved onto the stack and a smaller copy test. A CoreMark-only build keeps the standard 2 kB data.
- Boot: hello_world printed `Hello World! lp_mspm0l1306/mspm0l1306`; blinky passed the project's serial LED check.
- Run: every benchmark image first stopped at `***** HARD FAULT *****` in `sys_heap_init`. Zephyr's C library heap defaults to all RAM left over (8 to 16 bytes here), and setting up a heap that small writes past the end of RAM. Fixed with `CONFIG_COMMON_LIBC_MALLOC_ARENA_SIZE=0`.
- Verified: CoreMark "Correct operation validated" at -Os, -O2, -O2 with unrolling, and true -O3: 41.99, 53.73, 59.70 and 56.74 per second. Every thread's stack had bytes left. The neural-net checksums match the G3507's and CC2340R5's. Interrupt latency through Zephyr: 119 to 137 cycles, after moving the test to an interrupt line this chip implements (it has 13 of 32; the first choice, line 28, read 17.7 million cycles).

**The line.** RAM, and Zephyr's defaults more than the chip. **Unknown (suspected: Chip limit).** As shipped, synchronization needs 6.1 kB, logger 8 kB, shell_module 12.5 kB and philosophers 17 kB; Zephyr's default interrupt stack alone is 2 kB, half the chip. Trimmed later the same day, the shell (48 bytes left), logger, synchronization and all eight Thread-Metric tests ran on the board (`mspm0l1306/zephyr/extra/README.md`); latency_measure crashed after its first result, and philosophers was not run.

- Trace why latency_measure faults in `z_setup_new_thread` with 256-byte test stacks.
- `CONFIG_MINIMAL_LIBC` instead of picolibc, to win back flash and some RAM.
- Upstream the board and the two driver fixes, so the next person gets `west build -b lp_mspm0l1306`.

**Ask.** Does Zephyr's MSPM0 maintainer group want an `lp_mspm0l1306` board, given how little RAM is left? Should the C library heap refuse a region too small to hold its own header, instead of writing past it?
