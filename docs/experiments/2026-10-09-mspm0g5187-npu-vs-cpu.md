# How much faster is the TinyEngine NPU on a TI LP-MSPM0G5187 than its own CPU?

**Short answer.** On the 8.5k-weight room-occupancy model the NPU takes 2.12 ms at 80 MHz. Against TI's own CPU build of the same model (NNC, 45.64 ms) that is 21.6 times faster, the like-for-like pair: same compiler, same clock, both timing the model call only. Against the fastest plain C build (35.27 ms at -O3) it is 16.7 times; that pair is not like for like, because the plain C figure also includes the input quantization (the plain C model call alone is 34.33 ms, so 16.2 times). All 20 test vectors gave the same class in every build. The gain shrinks at both ends: 3.8 and 3.0 times on the 636-weight model, 2.3 and 1.9 times on the 32.8k-weight model, by the two baselines. Every time on this page is the fastest of the 20 vectors, best of 5 calls each: a best case, not a typical or worst-case latency; the slowest vector ran at most 3.3 percent longer. Measured on 2026-10-08 and 2026-10-09 on a LaunchPad development kit with MSPM0 SDK 2.11.00.07.

Terms: [vocab](../vocab.md). Board page and fixes: [LP-MSPM0G5187 README](../../mspm0g5187/README.md) and [FAQ](../../mspm0g5187/FAQ.md). 1 kB = 1,024 bytes. NPU is the chip's neural processing unit. NNC is TI's neural network compiler.

**Question.** Does the NPU make a small neural network fast enough to matter, and where does the gain stop?

**Vendor position.** TI rates the NPU at 2.56 billion operations a second at 80 MHz (data sheet SLVSJB5B, rev. B, March 2026). The SDK READMEs for the edge-AI examples give CPU and NPU pairs on this chip: waveform classifier 54.06 ms and 5.84 ms, PIR 61.56 and 5.25, gesture 99.7 and 9.07, fall 8.56 and 0.67, character recognition 89.81 and 6.05 (read 2026-10-07).

**What was tried.** Four room-occupancy models (500, 2k, 8k and 30k parameters, int8, 20 test vectors each), compiled four ways: plain C at `-Os` and `-O3`, TI's NNC for the CPU, and TI's NNC for the NPU. One image per model and build, run bare metal on the MSPM0G5187 with TI Arm Clang 5.1.1.LTS. Each vector is run once to check the class and then five times; the table shows the fastest run of the fastest vector, timed with SysTick on the CPU clock. TI's own CPU and NPU example pairs were also timed with a wrapper that times `tvmgen_default_run` and changes none of TI's source.

**How far it got.** Verified. Every image matched the expected class on all 20 vectors.

**What each number is (read this before the tables).** The harness runs each of the 20 vectors once to check its class, then five more times and keeps the fastest; the table shows the fastest vector of those twenty. That is a best case. The slowest vector is in the saved captures and in the results store (`value_hi`): on the NNC and NPU builds it ran 0.1 to 3.3 percent longer than the fastest (8k on the NPU: 2.116 to 2.155 ms), and both figures were identical on all three runs, so the three runs show repeatability of that statistic, not the application's worst case. No per-call samples were kept, so there is no distribution, no median and no 95th percentile here; the count of operations is fixed per model, which is why the spread is small. The clock covers the model call only (`tvmgen_default_run` to `tvmgen_default_finished`) on the NNC CPU and NPU builds, and input quantization plus the model call on the plain C builds (the model call alone is also in those captures as `runq`). None of this is a pipeline time: no sensor read, no feature extraction, no sleep or wake.

Two baselines, both from the rows in `data/results/mspm0g5187.csv`: the first table below sets the NPU against the fastest plain C build (not like for like, as above); the second sets it against TI's own CPU build of the same model, the pair TI's examples use.

|---|--:|--:|--:|--:|--:|
| 500 parameters | 3.92 ms | 4.94 ms | 1.29 ms | 3.0x | 2.88 ms |
| 2k | 9.05 ms | 11.98 ms | 1.45 ms | 6.2x | 3.23 ms |

## NPU against CPU, same model, same clock (rerun 2026-10-09, three runs)

**Expectation, written before the rerun.** The first table compares the NPU with plain C at `-O3`. The fair pair for "what the NPU adds" is TI's own compiler on both sides, same clock, so the NPU gain should read larger than 3.0, 6.2, 16.7 and 1.9 times (NNC's CPU code is slower than plain C `-O3`), the 32.8k-weight model should stay the weakest because one layer stays on the CPU, and the gain should not depend on the clock (the NPU runs from the CPU clock). For energy: the NPU build spins the CPU while it waits, so the chip should draw about the same current in both builds and energy per inference should fall about as fast as time does.

**Method.** Four models, each as TI NNC CPU code (`ti-npu type=soft`) and as TI NNC NPU code, at 80 MHz and at 32 MHz (the 32 MHz CPU build is new). Each image was erased, flashed and run three times, 20 of 20 test vectors right on all 48 runs. The fastest-vector cycle count was identical on every run, so the three runs agree to the cycle.

| Model | Multiply-adds | Clock | CPU | NPU | Speed-up | CPU cycles per multiply-add | NPU cycles per multiply-add | Runs |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| occ_cnn_500 | 11,328 | 80 MHz | 4.938 ms | 1.292 ms | 3.8x | 34.9 | 9.1 | 3 |
| occ_cnn_500 | 11,328 | 32 MHz | 10.853 ms | 2.880 ms | 3.8x | 30.7 | 8.1 | 3 |
| occ_cnn_2k | 33,856 | 80 MHz | 11.978 ms | 1.451 ms | 8.3x | 28.3 | 3.4 | 3 |
| occ_cnn_2k | 33,856 | 32 MHz | 26.593 ms | 3.229 ms | 8.2x | 25.1 | 3.0 | 3 |
| occ_cnn_8k | 157,824 | 80 MHz | 45.644 ms | 2.116 ms | 21.6x | 23.1 | 1.1 | 3 |
| occ_cnn_8k | 157,824 | 32 MHz | 101.015 ms | 4.771 ms | 21.2x | 20.5 | 1.0 | 3 |
| occ_cnn_30k | 610,560 | 80 MHz | 159.219 ms | 69.396 ms | 2.3x | 20.9 | 9.1 | 3 |
| occ_cnn_30k | 610,560 | 32 MHz | 357.439 ms | 161.009 ms | 2.2x | 18.7 | 8.4 | 3 |

**Result.** The expectation held on all three counts. Against TI's own CPU code the NPU is 3.8, 8.3, 21.6 and 2.3 times faster at 80 MHz, and the numbers barely move at 32 MHz (3.8, 8.2, 21.2, 2.2). The 8k model is the sweet spot at about 1 cycle per multiply-add; the 636-weight model pays for NPU set-up per layer, and the 32.8k-weight model runs one convolution on the CPU (9.1 cycles per multiply-add). Cycles per multiply-add are a little lower at 32 MHz than at 80 MHz on both sides, probably flash wait states at the higher clock (not checked); time still scales with the clock.

**Energy per inference (EnergyTrace), two quantities.** EnergyTrace works on this board through `tools/energytrace/etcap.py` on this Mac (probe <probe serial>, 3.3 V from the probe, 2 kHz sampling). The probe reads everything on the target side of the isolation block: chip, LEDs, the audio circuits behind J6 and the probe's own floor, about 16.4 mA with the chip asleep in WFI at 80 MHz (not split; the split needs shunt changes on the board). Running a model in a loop adds 0.4 to 0.7 mA on top, about the same in the CPU and NPU builds, so energy follows time. Both figures below are current x 3.3 V x the model's best-case latency from the timing rows: a steady loop that never sleeps, not an integrated single inference, so a lower bound per inference and no guide to a product that sleeps. "Above idle" is the loop reading minus the same model's idle reading (its ordinary image asleep in WFI after its check), paired run by run; the subtraction of two readings that differ by 3 percent spreads 7 to 32 percent between runs, so the range is shown. The rows are in `data/results/mspm0g5187.csv`.

| Model | Above idle, CPU (median, min to max of 3) | Above idle, NPU | NPU saves (medians) | Whole board, CPU | Whole board, NPU | Loop current CPU / NPU | Idle |
|---|--:|--:|--:|--:|--:|---|--:|
| occ_cnn_500 | 8.73 uJ (8.39 to 8.96) | 2.31 uJ (1.92 to 2.33) | 3.8x | 276 uJ | 72 uJ | 16.90 to 16.96 / 16.90 to 16.95 mA | 16.37 to 16.45 mA |
| occ_cnn_2k | 21.34 uJ (19.13 to 22.65) | 2.36 uJ (2.04 to 2.60) | 9.0x | 673 uJ | 81 uJ | 16.95 to 17.05 / 16.94 to 17.00 mA | 16.46 to 16.51 mA |
| occ_cnn_8k | 85.71 uJ (75.76 to 94.29) | 4.23 uJ (4.02 to 4.92) | 20.3x | 2,553 uJ | 119 uJ | 16.95 to 17.04 / 17.02 to 17.08 mA | 16.38 to 16.45 mA |
| occ_cnn_30k | 303.17 uJ (291.08 to 353.61) | 92.29 uJ (91.60 to 120.92) | 3.3x | 8,928 uJ | 3,857 uJ | 16.98 to 17.02 / 16.84 mA | 16.31 to 16.44 mA |

The whole-board ratios are 3.8, 8.3, 21.5 and 2.3 times, the same as the time ratios because the current is the same; the above-idle ratios land near them but carry the spread of the subtraction (the 500 and 32.8k-weight models' above-idle ranges overlap less than a factor of two from run to run, so read those two ratios as rough). No pair came out negative or inconclusive. The expectation held: about the same current, energy follows time. For a battery product, a loop that never sleeps hides the real gain. A product that wakes once a second spends almost all its energy asleep, and there the NPU's shorter run is what counts; the sleep current was not measured here, and no battery life can be given from these rows.

**Also repeated three times (TI's own example pairs, model call only).** Hello world 126.311 ms to 12.990 ms (9.7x, 32 MHz), gearbox fault 37.113 to 9.653 (3.8x, 32 MHz), motor bearing 106.798 to 1.283 (83x, 80 MHz), waveform classifier 54.307 to 5.858 (9.3x, 80 MHz, median of the fastest call kept per run). The waveform NPU run kept 10 calls per run and the spread across them was 5.85 to 6.02 ms.

Every row is in `data/results/mspm0g5187.csv`. The board was put back to TI's factory image afterwards; main flash and data flash read back identical to the backup.

**The line.** No limit reached; the gain depends on the model. The 636-weight model does little work per layer, so the NPU's setup per layer takes a large share of its 1.29 ms. In the 32.8k-weight model, NNC's compile log says `GCONV layer NOT offloaded to TI-NPU`, so that layer runs on the CPU and the NPU gain drops to 1.9 times. The NPU runs from the CPU clock: at 32 MHz the 8k model takes 4.77 ms, 2.25 times longer than at 80 MHz. The motor bearing pair is the odd one: TI's README lists the NPU version as slower than the CPU one, while the model-call-only timing here gives 83 times faster. TI's figure covers the whole example including the feature extraction, the timing here covers the model call, so they do not compare.

If a debugger reset lands while an earlier NPU run is still in progress, the next run hangs waiting for `tvmgen_default_finished`: the first vector passes and the second never ends, and NVIC shows the NPU interrupt pending. If you see that, start the image by flashing with DSLite and read the results after a wait, with no debugger reset. Five of this repo's first six NPU runs hung this way before resetting was stopped; the cause is this repo's, not the chip's.

**Ask.** Has anyone seen the NPU interrupt stay pending after a debugger reset on a G5187, and does a power cycle clear it?

## TI's other examples (ECG, fall, fan blade, character)

These four examples wait for a sensor (ECG front end, motion sensor, accelerometer) or for TI's drawing GUI, so on a bare board they never call the model. The build keeps everything of TI's (model library, SysConfig, clock) and swaps only `main()` for a small benchmark `main()`, which does the same start-up (including the NPU power-up on the NPU builds) and then calls the model 12 times on one fixed input. Timing is the same wrapper as the other examples: model call only, to the NPU done interrupt on the NPU builds, first 10 calls kept, 80 MHz, three runs each with a full erase, flash and run. Layer cost does not depend on the input values, so a fixed input times the same as a sensor frame.

Expectation, written before the runs: CPU and NPU times near TI's README figures, a 10 to 13 times speed-up on fall, fan blade and character, and for ECG (no TI latency) 60 to 150 ms on the CPU and 5 to 15 ms on the NPU.

| Model | Parameters (TI README) | CPU | NPU | Speed-up | Flash CPU / NPU | RAM CPU / NPU |
|---|--:|--:|--:|--:|--:|--:|
| fan blade fault (MLP, 3x128 input) | 5,228 | 1.762 ms | 0.182 ms | 9.7x | 1.43 / 2.13 kB | 1.00 / 0.85 kB |
| fall detection (CNN, 3x64) | 6K | 8.566 ms | 1.435 ms | 6.0x | 12.6 / 13.8 kB | 0.94 / 0.71 kB |
| ECG anomaly (CNN, 2.5k samples) | 55k | 496.5 ms | 96.6 ms | 5.1x | 63.5 / 86.9 kB | 18.0 / 12.9 kB |
| character recognition (CNN, 28x28 float) | 60,000 | 91.94 ms | 10.13 ms | 9.1x | 66.4 / 71.4 kB | 8.0 / 10.7 kB |

Flash and RAM are the model's own objects from the linker map (weights, model code, NNC runtime, model buffers); the image around them is excluded. They agree with the figures in TI's READMEs (ECG CPU 65.0 kB (decimal) against TI's 64.8 kB and 18.4 kB of RAM against 18.4 kB; fan blade NPU 2.18 kB against 2.178 kB). Every run of a build gave the same cycle count to the cycle (the models have no data-dependent branches), so the spread is zero.

What did not match the expectation:

- ECG is slow on both: 496.5 ms on the CPU (about 3 times the high guess) and the NPU gain is only 5.1 times, so one 2.5k-sample window takes 97 ms even on the NPU. TI publishes no latency for it.
- Fall detection on the NPU took 1.435 ms where TI's README says 0.67 ms (this repo's time ends at the NPU done interrupt; how TI timed it is not stated). The CPU matched TI's 8.56 ms (8.566). Gain 6.0 times, not 12.8.
- Character recognition: the CPU matched TI (91.94 against 89.81 ms); the NPU took 10.13 ms against TI's 6.05 ms. The model takes and returns float32, so the NPU build converts at the edges.
- Fan blade ships at the 32 MHz default clock (4.112 ms CPU, 0.406 ms NPU there). The table is at 80 MHz, set with the same clock-tree lines TI's own waveform example uses; nothing else in its SysConfig changed.

Output check. No example ships input data, so TI's expected output cannot be compared. What was checked: the CPU and NPU build of each model, given the same fixed input, return the same answer. ECG (-75, 26, -127, 52), fan blade and character recognition match exactly; fall detection differs by one count in one output (CPU 11, -76; NPU 11, -77), the same class. The character output is saturated at -2.0 for the first three classes on this synthetic input, so that one is a weak check.

Parameters come from each example's README ("Number of Parameters"). MACs: TI does not publish them for these examples (README tables list parameters, accuracy, flash, RAM and latency only) and the model library carries no layer shapes, so MACs are not given.

The board's flash was backed up on this Mac before the runs (TI's factory image) and restored with OpenOCD `program ... 0x0 verify`; main flash (128 kB) and data flash (8 kB) read back identical.
