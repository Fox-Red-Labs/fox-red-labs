# Can Zephyr run on the AM62L's Cortex-A53 from on-chip SRAM with the DDR never initialized?

**Short answer.** Yes, for hello world. A JTAG load of the 124 KB `build-sram-all` image into the 144 KB of SRAM at 0x707F0000 starts one A53 core at EL3, and UART0 prints `*** Booting Zephyr OS build a915b2f12675 ***` and `Hello World! am62l_evm/am62l3/a53`. UART0 is clocked and on rate with no TIFS firmware, no TF-A and no DDR running. The pin-control write that Zephyr makes at start-up landed, so the pad partition is unlocked once the boot ROM has run. The earlier Renode run (the same image booting in a simulator) held on the chip. Terms: [vocab](../vocab.md). FAQ: [AM62L](../../am62l-evm/FAQ.md). 1 KB = 1,024 bytes.

**Question.** Can Zephyr run on one A53 core of the AM62L from the chip's on-chip SRAM, with the LPDDR4 never initialized and no firmware under it, and does the console UART work in that state?

**Vendor position.** The AM62L evaluation module user guide (SPRUJG8B, tables 2-5 to 2-9) gives the boot-mode switch settings; the shipped settings are full pincount, BOOTMODE 0x0243, primary boot from the SD card (MMCSD port 1), no backup, 25 MHz clock. Zephyr's `am62l_evm` board in upstream (commit a915b2f) is written for a start from U-Boot with the DDR up and TF-A and TIFS running; its documentation loads the image from U-Boot or debugs it with OpenOCD newer than 0.12.0. No document read for this run describes a start with the DDR off.

**What was tried.** 2026-10-21 on an M4 Mac with CCStudio 21.0.1 (DSLite 21.0.0.4166) and the board's on-board XDS110 (firmware 3.0.0.32; DSLite warns it wants 3.0.0.43 and proceeds). Boot switches as shipped, with no SD card in the slot, so the boot ROM waits in its SD loop. Image: `build-sram-all` (`am62l-evm/zephyr/sram-all.overlay` plus `bare-el3.conf`: one core, EL3 entry, no SCMI, no PSCI, UART0 only, 8 translation tables), one load segment at 0x707F0000, entry 0x707F08BC, built on a second Mac against Zephyr a915b2f. Connection: `am62l-evm/tools/load_sram.sh --list-cores` shows CortexA53_0, CortexA53_1 and SMS_CM4_0_TIFS. The stock CCStudio board file's A53 startup script (GEL) sets the PLL and runs the DDR initialization on connect, so the run uses a copy of the board file with the GEL removed (`am62l-evm/tools/AM62L_TMDS62LEVM_nogel_board.xml`) and a connection file that lists all the drivers the A53 needs (`cortexA53`, `cortexM`, `etbcs`, `csstm`, `ctset2` beside the DAP driver; with only the DAP driver DSLite answers "An invalid processor ID has been found"). `load_sram.sh --listen --core 0` halts A53_0 in the ROM's wait loop, writes the ELF, sets the program counter to the entry point and leaves the core running. UART A (the FT4232 port A, the SoC's UART0) is read by `am62l-evm/tools/capture.py`, which opens the port and sets 115200 itself. Files: `am62l-evm/tools/`, `am62l-evm/zephyr/`.

**How far it got.** Configure, compile, link, load, run and verified. The capture log has the banner and the hello line 9.836 s after the capture started; the 9 s is DSLite's connect and load, not the chip. Reads after the run (`load_sram.sh --peek`): the kernel's current thread is the idle thread (main returned), the UART0 line-status register reads 0x60 (transmitter empty), the mode register MDR1 reads 0, and the pad registers for UART0 RXD and TXD (0x040841B4 and 0x040841B8) hold 0x00050000 and 0x00010000, the values Zephyr's pin-control driver writes. Separately, a 'U' stream image (`am62l-evm/zephyr/apps/uart-stream`, a polled `uart_poll_out` loop) produced 11.6 kB/s of clean 0x55 bytes, which is 115200 baud at 10 bits per byte, so the line rate is exact.

**The line.** No stop. The numbers: 124 KB image in a 144 KB map (20 KB spare); one core at EL3; DDR never initialized; no firmware under it. What the run does not show: any speed (no CoreMark, no memory timing), any boot time (the 9 s is the debugger, and the ROM was not involved), any power figure, whether the boot ROM accepts the image as its phase-1 payload (not run; it needs a signed image and the UART boot setting), the second A53 core, or any peripheral beyond UART0. The load went through the debugger, so this says the chip can run the image, not that a product could start it that way. A serial lesson from the run: on macOS a baud set with `stty -f` in one command reverts when that command closes the port, so a following `cat` reads at 9600 and a 115200 line looks silent; set the rate in the same program that reads.

**Ask.** If you know the AM62L boot ROM's maximum phase-1 image size or the format it expects for a UART-boot payload, say the TRM (SPRUJB4) section. If you have run a K3 A53 from SRAM with the DDR off and a different UART setup, say what you saw.
