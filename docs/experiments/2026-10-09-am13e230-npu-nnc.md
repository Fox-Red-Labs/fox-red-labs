# Does TI's compiler put this repo's room-occupancy models on the LP-AM13E230's NPU, and how much faster is it?

**Short answer.** Yes. The NPU build matched the expected class on 20 of 20 test vectors in every run and took 0.107, 0.205, 0.630 and 9.535 ms on the 636, 1,748, 8,484 and 32.8k-weight models at 200 MHz. TI's own CPU build of the same model on the same core, clock and compiler took 0.499, 1.376, 5.544 and 22.91 ms, so the NPU is 4.7, 6.7, 8.8 and 2.4 times faster. The software-only build is verified the same way. The CDE build (custom instructions on the Cortex-M33) does not work: it compiles only after a compiler error is turned into a warning, and then the board halts before the first result.

Terms: [vocab](../vocab.md). 1 kB = 1,024 bytes. NNC is TI's Neural Network Compiler. NPU is the chip's TinyEngine neural processing unit. CDE is the Arm Custom Datapath Extension.

**Question.** Does a model compiled by TI's NNC 2.1.2 run on the AM13E230's NPU and give the right answers, and does the CDE build do the same?

**Vendor position.** NNC 2.1.2 supports "AM13x and Arm Cortex-M33 core based devices" with three targets (NNC user's guide 2.2.4, <https://software-dl.ti.com/mctools/nnc/mcu/users_guide/compiling.html>, read 2026-10-09): the NPU (`--target="c, ti-npu"`), plain CPU (`type=soft`) and CDE (`type=m33cde`, compiled with `-march=thumbv8.1-m.main+cdecp0`). The guide says nothing about which compiler versions the CDE path was tested with, and its setup example names `ti-cgt-armllvm_4.0.3.LTS`; this repo used 5.1.1.LTS, the version the AM13E2x SDK asks for.

**What was tried.** The four models (the `occ_cnn_*` int8 ONNX models, 636 to 33k weights) compiled three ways with the guide's Cortex-M33 options. NNC 2.1.2 has no build for an Intel Mac, so the compile ran on a Linux machine through a GitHub Actions workflow: one run built the NPU and software targets for all four models, a second built the CDE target. Each result was linked on this Mac with TI Arm Clang 5.1.1.LTS and the AM13E2x SDK and run from flash at 200 MHz: 20 vectors checked, then one `tvmgen_default_run` call timed with the DWT cycle counter, best of 5 per vector, fastest vector quoted. Three runs per image, each a full erase, flash and run. Rows: `data/results/am13e230.csv` (`ai_occ_latency`, variants `-npu`, `-nnc-cpu`, `-nnc-cde`).

**How far it got.** Verified for the NPU and software builds: 24 of 24 runs matched 20 of 20 vectors, and the fastest-vector cycle count was identical across the three runs on 7 of 8 builds (the 500-model NPU build differed by 11 cycles on one run, 21,333 against 21,344). The CDE build reached link and flash, and failed at run.

| Model | Multiply-adds | NNC CPU build | NNC NPU build | Speed-up | Runs |
|---|--:|--:|--:|--:|--:|
| occ_cnn_500 | 11,328 | 0.499 ms | 0.107 ms | 4.7x | 3 |
| occ_cnn_2k | 33,856 | 1.376 ms | 0.205 ms | 6.7x | 3 |
| occ_cnn_8k | 157,824 | 5.544 ms | 0.630 ms | 8.8x | 3 |
| occ_cnn_30k | 610,560 | 22.91 ms | 9.535 ms | 2.4x | 3 |

Expectation, written before the run: 3 to 10 times on the 1,748- and 8.5k-weight models, with the 32.8k-weight model possibly losing a layer to the CPU. Both held (6.7 and 8.8 times; the 32.8k-weight model gains 2.4 times). The sibling experiment on the MSPM0G5187 is [mspm0g5187-npu-vs-cpu](2026-10-09-mspm0g5187-npu-vs-cpu.md); the full AM13E230 write-up, including the plain C comparison, is in [RESULTS-am13e230](../../am13e230/RESULTS-am13e230.md).

**The line.** Two limits, one of them hard.

- The CDE target. With the guide's options (`type=m33cde`, `-march=thumbv8.1-m.main+cdecp0`) the last compile step fails on all four models with `error: incompatible pointer types passing 'const uint32_t[16]' to parameter of type 'const int8_t *'` in NNC's generated `lib2.c` (`TINIE_fullyConnectedCDE`, and the bias argument of `TINIE_convolveCDE`), and `mod.a` is never written. With `-Wno-error=incompatible-pointer-types` a library comes out. Flashed, the image takes an instruction bus error before the first result: CFSR 0x00000100, HFSR 0x40000000 (FORCED), result block empty after 8 s, 0 of 20 vectors, on all four models, with the coprocessor-access bit for CDE set in CPACR or not. Cause unknown (the bus error is an instruction fetch; the faulting address was not read).
- The 32.8k-weight model gains least. NNC's compile log says `GCONV layer NOT offloaded to TI-NPU` (the weights could overflow the NPU's 18-bit accumulator), so one convolution stays on the CPU, as on the G5187.

**Ask.** Has anyone run NNC's `type=m33cde` output on an AM13E2x, and with which compiler version? If the bus error comes from pairing NNC 2.1.2 with Arm Clang 5.1.1, please say so.
