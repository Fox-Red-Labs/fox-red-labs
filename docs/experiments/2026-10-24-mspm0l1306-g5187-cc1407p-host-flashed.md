# Does the bare-metal CC1407P host build run on the LP-MSPM0L1306 and the LP-MSPM0G5187 after it links?

**Short answer.** It runs on both, up to the point a radio is needed. Each board printed its banner, pulsed the radio's reset, asserted chip select and clocked out the driver's first frame, `00 04 11 00 02 32 00 00 e9 71`, the same ten bytes the LP-MSPM0G5187 sent in its recorded link of 2026-10-10. No radio was wired, so no reply was judged. The L1306 image is 14.1 kB of flash and 2.2 kB of RAM with a 4-buffer pool.

Terms: [vocab](../vocab.md). Files: `mspm0l1306/radio-host/` (new build for the L1306) and `mspm0g5187/radio/`. Checked 2026-10-24 with TI Arm Clang 5.1.1.LTS, SDK 2.11.00.07, SysConfig 1.28.0 (unvalidated).

**Question.** An earlier pass linked the host driver for nine boards and measured size only. Does the linked image start and behave on two of them?

**Expectation.** From the G5187 trace of 2026-10-10: `Cr R t c p S0a>` then the ten-byte frame. With nothing on the bus the reply is not meaningful.

**Result.**

| Board | Seen |
|---|---|
| LP-MSPM0G5187 | banner, `CrRtcpS0a>0004110002320000e971<00...`, reply all `00` (POCI low) |
| LP-MSPM0L1306 | same banner and frame, reply all `ff` (POCI high); then the driver waits inside the SPI-complete handler (halted in `hb_delay_us`, 3 s after reset) |

**The line.** The radio, wired to SPI0 PA6, PA5, PA4, PA3, PA7 and PA2 on the L1306, closes it. The 4-buffer pool is TI's driver with one constant changed; whether it works with so few buffers is unknown until a radio answers.

**Gotcha found.** `mspm0g5187/radio/radio_host.c` prints "LP-MSPM0G5187" in its banner whichever board runs it.
