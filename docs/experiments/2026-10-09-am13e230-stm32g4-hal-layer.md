# Does STM32G4 HAL code run on the LP-AM13E230 through TI's compatibility layer?

**Short answer.** Yes for GPIO, UART and DMA, with two catches. All five of TI's layer examples build and run on the board (SPI only as far as it can without a second board). ST's own GPIO toggle and UART printf examples, written for a different chip family, run on it with 3 and 7 lines inserted into ST's `main.c` and no line of ST's changed. But the layer has no timer, no ADC, no clock tree and no I2C, and every delay and timeout you pass it is counted in CPU cycles, not milliseconds. ST's timer examples fail at the first compile.

Contents: the question, TI's position, what was tried, how far it got, edits to ST's examples, the line, where it stopped, ideas, the ask, what to do next, then four questions with answers.

Terms: [vocab](../vocab.md) (HAL, DriverLib, SysConfig, shim). Board page: [LP-AM13E230 README](../../am13e230/README.md), [FAQ](../../am13e230/FAQ.md). HAL is ST's driver library. "The layer" here is TI's `source/compatibility/stm32g4_hal`, a re-implementation of ST's STM32G4 HAL function names on top of TI's driverlib. Code and scripts: `am13e230/stm32g4-hal/`. DSLite is UniFlash's command-line flasher. A unicomm is one of the board's serial-capable peripheral blocks; the layer's `USART2` and the USB serial port of the LaunchPad development kit sit on different ones. 1 kB = 1,024 bytes on this page. Run 2026-10-09 on macOS 15.7 (Intel) with the AM13E2x SDK 26.01.00.03, TI Arm Clang 5.1.1.LTS, SysConfig 1.28.0 and DSLite from UniFlash 9.6.0.

**Question.** TI aims the pin-compatible AM13E230 at teams with working STM32G4 code. How much of that code compiles and runs on the AM13E230 as it is, and where does the layer stop?

**Vendor position.** The SDK release notes (26.01.00.03) list "STM G4 Compatible drivers for following peripherals: DMA GPIO SPI UART" as supported, and "STM G4 Compatible drivers support for I2C MCAN" and "Limited examples for STM G4 Compatible drivers" under "What Is Not Supported". Each of the five examples says it shows "that existing STM32G4 HAL [GPIO, DMA, SPI, UART] code can run with minimal modifications". TI's STM32G4 migration guide (SDAA226, March 2026) compares pins, peripherals and clocks; the word HAL does not appear in it, so the layer is documented only in the SDK's example pages and the release notes. Checked 2026-10-09.

**What was tried.**

1. Built TI's five LaunchPad examples with this repo's own script (`build.sh`, same compiler flags and prebuilt libraries as the SDK's other examples, no CMake), flashed each with DSLite and checked it.
2. Counted the layer's coverage: every function the layer's headers declare against every symbol in its prebuilt library (`libstm32g4_hal_ti_sdk_cfg_default_m33_ti_arm_clang.a`, read with `tiarmnm`).
3. Took ST's own examples for the NUCLEO-U083RC from STM32CubeU0 v1.3.0 (the same ones run on that ST board): the HAL GPIO toggle, the HAL UART printf, and for timers the HAL `TIM_DMA` (PWM through `HAL_TIM_PWM_Start_DMA`) and the LL `TIM_PWMOutput_Init`. Built each against the layer's headers with a stand-in `main.h`. Where it compiled, fixed only what the compiler named, and kept ST's `main.c` otherwise as shipped.

**How far it got.** Run for TI's three single-board examples and for ST's GPIO and UART examples. Built but not run end to end for the two SPI examples. Compile stopped for both ST timer examples.

Flash and RAM come from the linker maps (RAM is `RAM_S` plus `RAM_C`). The SDK's own prebuilt copies of the five TI examples also ran clean in the earlier sweep of this board.

**Edits to ST's examples.** Lines of ST's `main.c` unchanged, inserted and changed, then the TI-side files each example needs.

| Example | ST `main.c` lines | Unchanged | Inserted | Changed or deleted | Lines of ST code switched off | TI-side shim |
|---|--:|--:|--:|--:|--:|---|
| GPIO toggle | 204 | 204 | 3 | 0 | 32 | `main.h` 13 lines |
| UART printf | 310 | 310 | 7 | 0 | 48 | `main.h` 20 lines, MSP file 17, retarget file 13 |

What the inserted lines do. Both examples set the clock in a 32-line `SystemClock_Config` built on ST's RCC and PWR calls, which the layer does not have. `SYSCFG_DL_init();` was added (TI's clock setup from the `.syscfg` file) and the ST body was wrapped in `#if 0`. The UART example also needs `#if 0` around the prescaler and advanced-feature fields and the three `HAL_UARTEx_*` FIFO calls. The shim `main.h` stands in for ST's: it includes the layer's headers, maps `LED4` to PA5 (the same pin on both boards), turns ST's clock-enable macros into nothing, and redefines `HAL_Delay(ms)` to multiply by 200k cycles per millisecond. Its other jobs: `USART2` becomes `UART5` (the layer maps `USART2` to unicomm 1, but the USB serial port of the LaunchPad development kit is unicomm 4), and a small `BSP_LED_*` stand-in replaces ST's board support file. The UART MSP file replaces ST's 158-line `stm32u0xx_hal_msp.c` (RCC clock select, gate, alternate function 7) with TI's own pin setup on PA0 and PA1. The retarget file adds a `write()` that feeds each character to ST's `__io_putchar`, and turns off `stdout` buffering, because TI's C library only flushes on exit and the example never exits. TI's own `example.syscfg` for each example is used unchanged. ST's other files (`system_*.c`, `stm32u0xx_it.c`, `hal_conf`, `nucleo_conf`) are not used.

**The line.** The layer covers 65 of the 93 functions its headers declare.

| Part | Declared | In the library | Missing |
|---|--:|--:|---|
| Core (`HAL_Init`, tick, ids) | 19 | 3 | `HAL_DeInit`, `HAL_IncTick`, `HAL_InitTick`, `HAL_SetTickFreq`, `HAL_MspInit` and eleven more |
| GPIO | 8 | 8 | none |
| DMA | 11 | 11 | none |
| UART | 27 | 23 | `Transmit_DMA`, `Receive_DMA`, `RegisterCallback`, `UnRegisterCallback` |
| SPI | 28 | 20 | `Transmit_DMA`, `Receive_DMA`, `TransmitReceive_DMA`, `DMAPause`, `DMAResume`, `DMAStop`, the callback registers |

Beyond the function counts, four limits decide whether a given STM32G4 project moves:

1. **No clock, power or timer.** There is no RCC, PWR, TIM, ADC, I2C or CAN in the layer. Any project that sets its clock through ST's `HAL_RCC_*` or runs a timer, a PWM or a conversion needs those parts rewritten with TI's driverlib. **Tool or docs.** The release notes list I2C and CAN as not supported; the timer, ADC and clock gaps are not stated anywhere found.
2. **Time is in CPU cycles.** `HAL_Delay(x)` waits x cycles and `HAL_GetTick()` returns a 32-bit cycle counter at 200 MHz, which wraps every 21.5 s. ST's `HAL_Delay(100)` becomes 0.5 microseconds. Every timeout argument is in cycles too: ST's UART example passes `0xFFFF` as a transmit timeout, which is 0.33 ms, and a whole 70-byte string sent in one call with that timeout printed almost nothing until one character per call was sent, as ST's code does. **Tool or docs.** The unit is written once, as a comment in the SPI example's `main.c`, and nowhere on the example pages or in the headers.
3. **Peripheral instance numbers are TI's, not ST's.** `USART2` drives unicomm 1, not the pins ST's example sets up. The pin setup is not in the layer: each example brings its own MSP file with TI's `IOMUX_*` names. **Tool or docs.**
4. **Settings are partly ignored.** The UART code has a `TODO` for oversampling and one-bit sampling, so those fields are accepted and do nothing. **Tool or docs.** Parity, word length, stop bits and flow control are mapped and worked: ST's odd parity came out on the wire.

**Where it stopped.** For ST's two timer examples at the compile: the layer's headers define no timer type, no timer register names and no `stm32g4xx_ll_*` headers, so `main.c` fails on its first timer line. **Tool or docs.** That is a missing part of the layer, not a chip limit. The AM13E230 has timers and motor PWM units; TI's driverlib drives them, and the layer does not.

- An unmodified STM32CubeG4 example, as the question first asked, instead of the NUCLEO-U083RC ones. Only the STM32CubeU0 package is on this Mac. The U0 examples already differ from G4 ones in the clock calls, which is the part the layer drops either way.
- The two SPI examples against each other: a second board with an STM32G4 SPI slave, or one TI board per role with three jumpers (PA20, PB5, PB10) and a button press.
- Compiling the layer's source into the project instead of linking TI's prebuilt library, and adding `HAL_TIM_PWM_*` on top of driverlib's timer calls. The layer's source is 5 files, about 3,200 lines.
- ST's HAL interrupt-driven UART and DMA examples, which hit the missing `RegisterCallback`.

**Ask.** Would a team with real STM32G4 code put this layer into a product build? The question to someone with an STM32G4 project is which of its HAL calls beyond GPIO, UART, SPI and DMA it uses, since the timer, ADC and clock calls are the likely stop.

**What to do next.** The layer lets you keep ST's GPIO, UART, SPI and DMA code and its call names while you redo the clock, pins, timers and analog parts in TI's tools. In this repo's two ports ST's `main.c` kept every line it had, and the work was in the files around it. Check the delay and timeout units first: they compile without a warning and run wrong.

## Questions

### Why does `HAL_Delay(100)` return almost at once on the LP-AM13E230?

The layer counts cycles, not milliseconds. **Tool or docs.** `HAL_Delay(x)` waits x CPU cycles at 200 MHz, so 100 is 0.5 microseconds. Multiply your milliseconds by 200k, as this repo's shim `main.h` does. Source: `am13e230/stm32g4-hal/`.

### Why does a long `HAL_UART_Transmit` string print almost nothing?

The timeout is in cycles too. **Tool or docs.** ST's `0xFFFF` is 0.33 ms here, too short for a 70-byte string sent in one call. One character was sent per call, as ST's code does.

### Why does an STM32G4 timer, PWM, ADC or clock code fail to compile with `unknown type name 'TIM_HandleTypeDef'`?

The layer has no timer, ADC, RCC, PWR or I2C parts. **Tool or docs.** ST's `HAL_TIM_PWM_Start_DMA` example gave 90 errors and the LL timer example 87. Rewrite those parts with TI's driverlib.

### Why is the ST UART example's output garbled on the backchannel port?

The port needs 8 data bits and odd parity to read ST's setup. **Setup or handling.** Read as no parity, both lines come out garbled.
