# Can the TI LP-AM263P decode H.264 video, with no video hardware and no operating system?

**Short answer.** Yes, in software. h264bsd, an open-source baseline-profile decoder in plain C, runs on one Cortex-R5F at 400 MHz with no operating system and decodes a 640x360 stream at 26 frames per second (15.2M cycles per frame, built with -Os). The CRC of the first frame, the last frame and all 30 frames together match the same decoder on the Mac (`3f93a620`). There is no video hardware on the chip, and the LaunchPad has no display, so the check is the checksum.

Terms: [vocab](../vocab.md). 1 kB = 1,024 bytes. Board notes: [LP-AM263P README](../../am263p/README.md) and [FAQ](../../am263p/FAQ.md).

**Question.** Could the AM263P4 on the LaunchPad show or process H.264 video with what is on the chip, the SDK and open-source code?

**Vendor position.** The data sheet SPRSP81D (Rev. D, read 2026-10-09) lists the processing resources: "Single, dual, and quad-core Arm Cortex-R5F MCU with each core running up to 400MHz", "16KB I-cache ... 16KB D-cache", "256KB Tightly-Coupled Memory (TCM) with 32bit ECC per CPU core cluster", "3MB of On-Chip RAM (OCSRAM) 6 Banks x 512KB", and an octal SPI flash interface with execute-in-place. The feature list has no video encoder, video decoder, camera interface or display controller. The Cortex-R5F in this part has the VFPv3-D16 floating-point unit and no NEON (the SDK builds with `-mfpu=vfpv3-d16`). TI's E2E forum and the MCU+ SDK pages returned nothing for H.264 on AM263x, AM263Px or AM243x (searches 2026-10-09). The LaunchPad has no display or camera, so output can only be a checksum, or a frame read from RAM.

**What was tried.**

- Software: h264bsd (commit `42bcb5d`, 2022), `https://github.com/oneam/h264bsd`. Its files come from the Android Open Source Project, Apache-2.0, and its wrappers are MIT. It decodes baseline profile only (I and P pictures), written in plain C with no operating-system calls except `malloc` and `free`.
- Stream: the first 30 pictures (94.3 kB) of the repository's own `test_640x360.h264`: baseline profile, level 3.0, 640x368 coded and 640x360 cropped, one IDR and 29 P pictures, from a "Big Buck Bunny" clip. No ffmpeg on this Mac, so no stream of this repo's own was made.
- Program: `am263p/bench/h264/` (`h264_run.c` decodes the array and prints a CRC-32 of every frame; `r5_main.c` is the R5F platform; `host_main.c` is the Mac platform). The R5F build uses the SDK makefile pattern of the other bench programs (`am263p/tools/build_bench.sh`): `r5fss0-0_nortos`, TI Arm Clang 5.1.1, SDK 26.01.00.08, loaded into RAM with DSLite. `link_patch.py` rewrites the SDK's generated linker file: a 1.7 MB heap for the C library and an OCSRAM region of 2 MB, starting at the bottom of the RAM, with the two unused shared-memory regions moved out of the way. (The first attempt used 2.6 MB; see the line.)
- Mac reference (the expectation): the same sources and the same CRC code, compiled with `cc -O3` on macOS 15.7.9, Intel.
- Expectation for speed, before any run: this repo's estimate, with no source, is 100 to 200 cycles per pixel for a core with no vector unit, which gives 23M to 47M cycles per frame at 640x368 and 8 to 17 frames per second at 400 MHz.
- Commands to rebuild: `am263p/bench/h264/build.sh os` builds both, with the 2 MB layout (`H264_OCRAM_ORIGIN=0x70000000 H264_OCRAM_LEN=0x1F0000 H264_HEAP=1753088`). Run, with the serial port opened before the load:

```bash
python3 am263p/tools/run_imgs.py 1 "H264 END" 180 h264=<build folder>/h264os2.out
```

**How far it got.** Configure, compile, link, load into RAM, run, verified by CRC. No flash was written.

| Measure | Value |
|---|---|
| Mac reference, 30 frames, two passes | 30 frames both times, frame 1 CRC `8af3c2f8`, frame 30 `83a9d8bb`, all frames together `3f93a620` |
| Heap the decoder needs at 640x368 | 1.58 MB at its peak (exact byte count in `am263p/data/logs/h264-mac-reference.txt`), 13 allocations (about four 345 kB frame buffers plus the rest) |
| R5F image, -O3 | 285 kB of code and constants, of which the decoder is 144 kB of code and 4.9 kB of tables and the stream is 94.3 kB; heap reservation 1.8 MB |
| R5F image, -Os | 182 kB; decoder 43 kB of code |
| R5F, -Os, 3 passes, 30 frames | 457.4M to 457.5M cycles per pass, 15.2M per frame, 26.2 frames per second; the IDR picture 35.4M cycles, each P picture 10.9M on average (316.2M for 29) |
| Checksums on the board | frame 1 `8af3c2f8`, frame 30 `83a9d8bb`, all `3f93a620`: identical to the Mac in all three passes |
| Heap peak on the board | 1.54 MB on 32-bit pointers (the Mac's 64-bit pointers use 1.58 MB) |
| Speed against this repo's estimate | estimate 8 to 17 frames per second; measured 26 |

The one-IDR-plus-29-P-pictures test is a small clip: a 640x360 frame is 337.5 kB of picture data, so only a few frames can sit in RAM at once.

**The line.** No limit reached at 640x360. Two things to know. First, the memory: the layout built first (heap and code spread over 2.6 MB of OCSRAM, from the data sheet's 3 MB) loaded fine but printed nothing, not even the first line, so the program stopped before `main`. The same program with a 256 kB heap and a 1.75 MB region ran, so the board's RAM looks like 2 MB, not 3 MB (the part's RAM-size fuse nibble reads 0 and no table for it was found; unconfirmed). The run that worked uses all of 0x70000000 to 0x701EFFFF, which includes the 256 kB the SDK keeps for its bootloader (free here because nothing boots), with a 1.7 MB heap: about 4 frame buffers of 345 kB at 640x368. Second, the -O3 build is 285 kB against 182 kB for -Os and does not fit that layout with the heap; speed at -O3 is not measured.

Licenses (checked against each vendor's license text): h264bsd is Apache-2.0 plus MIT with no chip restriction and no click-through; no SDK license was accepted and no vendor code with restrictive clauses was used. The clip is a "Big Buck Bunny" excerpt (Blender Foundation, CC BY 3.0 per the film's page; not re-checked). H.264 itself is covered by patents held by a licensing pool; software that decodes it may need a patent license. That is a business question this page does not answer and is not legal advice.

- A 320x240 or 176x144 test stream (no ffmpeg here: `brew install ffmpeg` then `ffmpeg -f lavfi -i testsrc=size=320x240:rate=15 -frames:v 30 -c:v libx264 -profile:v baseline -pix_fmt yuv420p out.h264`), which cuts the frame buffers to 115 kB each and fits TCM-plus-OCSRAM with room to spare.
- Measure -O3 and -O2 (the code is 3 times larger at -O3) with the heap shrunk by decoding a smaller frame.
- Put the hot inner loops (`h264bsd_reconstruct`, the deblocking filter) in TCM instead of OCSRAM through the cache.
- Use the other three cores: decode slices on different cores (the stream would need several slices per picture) or run deblocking on a second core.
- Ethernet streaming from a Mac into the board's two gigabit ports (`enet` examples), decoding in RAM.
- The other decoders on the survey list: Cisco OpenH264 (BSD, larger, used in a Renesas FreeRTOS package), tinyh264 (a WebAssembly fork of h264bsd), minih264 (encoder).
- Writing a frame out as a PGM over the UART to look at it on the Mac.

**Ask.** Anyone who has run an H.264 decoder on an AM263x, AM243x or other Cortex-R5F without NEON: how many cycles per macroblock did you measure, and which decoder?
