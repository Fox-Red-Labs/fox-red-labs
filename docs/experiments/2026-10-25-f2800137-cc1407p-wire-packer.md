# Can a packer give the LAUNCHXL-F2800137 the same CC1407P wire bytes as an Arm chip?

**Short answer.** Yes for the transmit path. `portability/cc1407p-host/wire/` packs and unpacks 14 message types field by field. On the LAUNCHXL-F2800137 and on a Mac the stream is the same 315 octets (digest DC1DF5B1), and every message equals what TI's structs produce on a byte-addressed host. The driver itself is not changed to call it, and no radio was attached.

Terms: [vocab](../vocab.md). Follows [E244](2026-10-24-f2800137-cc1407p-host-shim.md). Code and results: `portability/cc1407p-host/wire/README.md`. Checked 2026-10-25, C2000 compiler 25.11.1.LTS, C2000Ware 26.02.00.00 LTS, probe <probe serial>.

**Question.** E244 ended with a different first message on the C28x. Does a packer that never lays a struct over a buffer fix the wire format?

**What we tried.** A field-by-field packer for 14 message types was built for the C28x and for a Mac, and the bytes it produces were compared with what TI's structs produce.

**Expectation.** Same bytes, because every offset is explicit and the only C28x differences are 16-bit `int` shifts and 16-bit `char`. The risk was a layout misread from the TRX.h comments.

**Result.** 17 of 17 cases equal on both targets (messages, the first transaction of TI's unmodified driver, a two-request transaction with padding and CRC, and radio-to-host parsing). A hand-moved offset fails the Mac test. The RAM image reads back identical bytes over the debugger. Cost: 677 words of code.

**The line.** What it does not show: RX, test and extended command layouts are not written. The reference is TI's structs plus one real driver transaction, not a capture of the full driver flow (it waits in `TRX_Host_open` for a radio). `LRF_*_byteCount` is half the octet count on the C28x, a trap for any port.

**Board state.** RAM load only. Flash read before and after: SHA-256 identical to the as-received image; TI's demo prints again.
