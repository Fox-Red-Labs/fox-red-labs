# How much H.264 video can the AM62L decode in software, from 320x240 to 1080p?

**Short answer.** One Cortex-A53 core of the AM62L (TMDS62LEVM, 1.25 GHz) decodes a 1080p30 baseline stream at 600 kbit/s in software at 34 fps, so a 1080p30 camera stream fits on one core with about 12 percent to spare. A 540x540 stream takes about 17 percent of one core at 30 fps. Main profile (CABAC, B-frames) at 1080p runs at 23.5 fps on one core and 35.5 fps on two. Every decoded frame matches the Mac's decode bit for bit.

Terms: [vocab](../vocab.md). FAQ: [AM62L](../../am62l-evm/FAQ.md). Streams and harness: `portability/h264/`. Rows: `data/results/am62l-evm.csv`, tests `video_sw_decode_fps` and `video_sw_decode_ram`.

**Question.** The AM62L has no video decoder block. Can its two A53 cores decode a 1080p, 30 fps, 600 kbit/s camera stream and a 540x540 stream in software, and how many cores does each need?

**Setup.**

- Board: TMDS62LEVM, TI Linux SDK 12.01.00.05.03, kernel 6.18.38, root file system on a USB stick, booted over UART. Both A53 cores at 1.25 GHz, performance governor. The LVGL demo service was stopped.
- Decoders: ffmpeg 8.0.1 from the SDK image (its native `h264` decoder, built with GCC 15.3.0), and the repo's h264bsd harness built on the board with GCC 15.3.0 `-O3`, single thread, timed with `CLOCK_MONOTONIC` around the decoder calls.
- Streams: `portability/h264/streams`, 30 frames each. The 540x540 stream (baseline, one reference frame, 15 fps); the Big Buck Bunny 640x360 clip; and the 30 fps streams capped at 600 kbit/s in baseline and in main (CABAC, two reference frames, two B-frames) at 320x240 to 1920x1080. For ffmpeg each stream was concatenated 10 times, 300 frames a run.
- Check: ffmpeg's MD5 of all decoded frames equals the Mac's ffmpeg 9.0.2 on all 9 streams. h264bsd's YUV CRCs equal the Mac build on all 4 baseline streams (the 640x360 clip gives `3f93a620`).
- Runs: 3 per point, median reported. Spread under 3 percent except one 2-thread 640x360 run.

Reproduce, from the repo on a Mac with the board on the network:

```
cd portability/h264/streams
for s in prof-baseline-1920x1080; do for i in $(seq 10); do cat $s.h264; done > x10-$s.h264; done
scp x10-*.h264 root@BOARD:/root/
ssh root@BOARD 'ffmpeg -hide_banner -benchmark -threads 1 -i x10-prof-baseline-1920x1080.h264 -f null -'
```

`-stream_loop` does not work on a raw `.h264` file (ffmpeg cannot seek it and stops with `Operation not permitted`); concatenate the file instead. Each copy starts with its own parameter sets and IDR frame, so it decodes as one stream.

**Result.**

| Stream | 1 thread | 2 threads | Frame time, 1 thread |
|---|--:|--:|--:|
| 540x540, baseline | 172.1 fps | 246.5 fps | 5.8 ms |
| 640x360 Big Buck Bunny, baseline | 174.7 | 245.1 | 5.7 ms |
| 320x240, 600 kbit/s, baseline | 451.1 | 538.6 | 2.2 ms |
| 640x360, 600 kbit/s, baseline | 231.7 | 310.2 | 4.3 ms |
| 1280x720, 600 kbit/s, baseline | 75.7 | 110.3 | 13.2 ms |
| 1920x1080, 600 kbit/s, baseline | 34.0 | 50.2 | 29.4 ms |
| 640x360, 600 kbit/s, main | 146.5 | 210.4 | 6.8 ms |
| 1280x720, 600 kbit/s, main | 52.6 | 77.0 | 19.0 ms |
| 1920x1080, 600 kbit/s, main | 23.5 | 35.5 | 42.6 ms |

ffmpeg on the AM62L, measured. User plus system time with one decoder thread is 99 to 122 percent of one core, because ffmpeg's reader and writer threads add to it. A second decoder thread gives 1.19 to 1.51 times, not 2: ffmpeg's frame threads share the two cores with its own reader and writer.

The repo's h264bsd decoder on the same board:

| Stream | fps | Cycles per pixel at 1.25 GHz | Decoder RAM (heap peak plus input buffer) |
|---|--:|--:|--:|
| 540x540 | 97.5 | 44.0 | 1.15 MB |
| 640x360 Big Buck Bunny | 102.8 | 52.8 | 1.61 MB |
| 1280x720, 600 kbit/s | 40.8 | 33.3 | 3.55 MB |
| 1920x1080, 600 kbit/s | 17.0 | 35.4 | 8.02 MB |

ffmpeg is 1.7 to 2.0 times faster than h264bsd on the same core.

**Against the expectation** (written before the run):

| Point | Expected | Measured | Verdict |
|---|---|---|---|
| 540x540, 1 thread | 80 to 140 fps | 172.1 | faster |
| 640x360 clip, 1 thread | 70 to 130 fps | 174.7 | faster |
| 1280x720, 1 thread | 30 to 55 fps | 75.7 baseline, 52.6 main | baseline faster, main within |
| 1920x1080, 1 thread | 12 to 25 fps | 34.0 baseline, 23.5 main | baseline faster, main within |
| 1920x1080, 2 threads | 22 to 40 fps | 50.2 baseline, 35.5 main | baseline faster, main within |
| 2-thread gain | 1.6 to 1.9 times | 1.19 to 1.51 | lower |
| h264bsd, 640x360 clip | 50 to 110 fps | 102.8 | within |

The earlier estimate "1080p30 no" holds for main profile on one core and is wrong for baseline: 34.0 fps on one core.

**Limits.**

- Decode only. Scaling, color conversion and display are not timed; the HDMI test in the battery shows that a CPU copy path to the display is slow on this chip (`data/results/am62l-evm.csv`, `gst_pipeline_fps`).
- The streams are a test pattern with a moving box. Camera footage at the same 600 kbit/s cap carries more detail per frame and costs more to decode; the 640x360 film clip cost 1.3 times the test pattern of the same size with h264bsd.
- Nothing else ran beside the decoder: no LVGL, no Matter link, no radar.
- Power during decode was not measured.
- One board, one SDK image.

**What this means.** On this evidence an AM62L decodes a 1080p baseline stream at 30 fps with one core, and a 540x540 stream with most of a core free. A main-profile 1080p stream needs both cores and leaves little for a user interface. At 1280x720 or smaller (both profiles under 20 ms a frame on one core) there is room for LVGL.
