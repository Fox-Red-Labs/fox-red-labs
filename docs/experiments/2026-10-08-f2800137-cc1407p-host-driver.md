# Can a C2000 LaunchPad (LAUNCHXL-F2800137, 16-bit char) host the BP-CC1407P radio driver?

**Short answer.** Not with TI's driver as it is. It does not compile for the C28x as shipped: 524 errors in 7 files, because the C2000 compiler has no `uint8_t` and rejects the GCC `packed` attribute the driver puts on 12 structs. Given C2000Ware's own `uint8_t` (16 bits) and with the attribute defined away by a compiler flag, all 7 files compile, but 11 of the 12 structs the driver lays over SPI bytes come out a different size than on Arm, and 29 shifts of event flags overflow a 16-bit `int`. So a C2000 host needs new code that packs and unpacks each message byte by byte; a recompile is not enough. Nothing was run: this is a compile check on a Mac, with no board or radio attached.

Terms: [vocab](../vocab.md) (C2000 and C28x, SPI, CRC, packed struct, bit field, byte order). Errors and fixes: [LAUNCHXL-F2800137 FAQ](../../c2000-launchpad/FAQ.md#libraries-written-for-8-bit-bytes). 1 kB = 1,024 bytes. Checked 2026-10-08 on macOS 15.7 (Intel) with TI's C2000 compiler 25.11.1.LTS.

**Question.** The BP-CC1407P is a radio that does not run your application: a host microcontroller drives it over SPI. Can a C2000 chip, whose smallest memory unit is a 16-bit word, be that host using TI's driver?

**Vendor position.** TI's product page for the BoosterPack, read 2026-10-07, says the plug-in ships a host driver "that can be ported to other MCUs". The supported hosts are five CC13xx and CC26xx LaunchPad development kits under the SimpleLink TRX plug-in 1.00.00.52. The LP-EM-CC2745R10-Q1 is also supported, under TI's Zephyr fork. No C2000 host is listed. The driver's own header defines its packed-struct macro for three compilers, IAR, "TI compiler" and GCC (`utility/utils.h`, lines 73 to 81), and says: "User must provide a definition for this macro if using a compiler other than the ones below."

The C2000 compiler's `stdint.h` defines `uint8_t` only for byte-addressed targets (MSP430, C55x byte mode, C6000, Arm, PRU, C7000, C29), not for the C28x. C2000Ware's driverlib adds its own: `typedef uint16_t uint8_t;` in `driverlib/f280013x/driverlib/inc/hw_types.h`, under the comment "Definition of 8 bit types for USB Driver code to maintain portability between byte and word addressable cores of C2000 Devices."

**What was tried.**

- **Driver source.** The SimpleLink TRX plug-in is not on this Mac. TI's Zephyr fork is: `simplelink-zephyr` tag `v3.7.0-ti-1.00.01_ga`, folder `drivers/misc/ti_cc140xp/host`, 10,958 lines. The plug-in is at `https://github.com/TexasInstruments/simplelink-trx-plugin` (or software-dl.ti.com, release 1.00.00.52). Whether its host folder is the same code was not checked.
- **Files compiled.** The 7 portable files: `trx_host.c`, `handlers/trx_host_handlers.c`, `private/trx_host_private.c`, `transport/spi_transport.c`, and the three in `utility/`. The two HAL files (`hal/platform_spi.c`, `hal/platform_util.c`) were left out. HAL means hardware abstraction layer: the small part of a driver that talks to one chip's peripherals, here Zephyr's SPI, GPIO and CRC calls, which every host writes for itself.
- **No change to TI's files.** This repo's stand-in for Zephyr's logging header compiles the log calls out (`c2000-launchpad/compile-checks/trx-host/stubs/`).
- **Compiler.** `cl2000 -v28 -ml -mt --float_support=fpu32 --abi=eabi --opt_level=2 --c99`, the flags of this repo's F2800137 bench builds. Three modes: the compiler's own types; C2000Ware's `uint8_t`; and C2000Ware's `uint8_t` plus `-D__packed__=`, which turns the packed attribute into an empty one.
- **Control.** The same 7 files and stubs for the Cortex-M33 with TI Arm Clang 5.1.1 and `-Wall`.
- **Sizes.** A small file of `sizeof` values for 12 message structs, compiled for both cores; the values are read from each compiler's assembly output.

| Build | Files compiled | Errors | Warnings |

| Cortex-M33, TI Arm Clang 5.1.1 (control) | 7 of 7 | 0 | 0 |
| C28x, compiler's own types | 0 of 7 | 524 | 80 |
| C28x, C2000Ware's `uint8_t` | 2 of 7 | 60 | 51 |

The 51 warnings in the last build: 29 `#64-D` shift count too large (item 3), 15 `#548-D` transfer of control bypasses initialization, 3 `#190-D` enumerated type mixed with another type, 2 `#69-D` integer conversion changed the sign, 1 `#303-D` typedef name already declared, 1 `#1-D` no newline at the end of a file. Only the shift warnings were followed up.

**1. No 8-bit type.** 479 of the 524 errors read `"TRX.h", line 73: error #20: identifier "uint8_t" is undefined` (445 times) or the same for `int8_t` (34). **Chip limit.** The C28x cannot address a single byte, so its compiler has no exact 8-bit type. C2000Ware's typedef clears these errors.

**2. The packed attribute.** The other 45 errors, and all 60 in the second mode, read `error #1167: invalid attribute for "struct TRX_Phy_s"` and the same for 11 more structs in `TRX.h`. **Tool or docs.** The driver writes `__attribute__((__packed__))` directly in `TRX.h` instead of the per-compiler macro in its own `utils.h`, and the C2000 compiler rejects it. On the C28x every member is already at least one 16-bit word, so packing has no meaning there; `-D__packed__=` removes it without editing TI's files.

**3. Event flags past bit 15.** With both fixes, 29 warnings read `warning #64-D: shift count is too large` (28 in `trx_host_handlers.c`, 1 in `trx_host.c`). **Tool or docs.** `trx_host.h` defines 15 event flags as `(1 << 16)` to `(1 << 30)`. `1` is an `int`, which is 16 bits on the C28x, so those shifts are undefined in C. The driver's last four flags already use `1ULL`; the others need the same. What this build does with them at run time was not checked.

**4. Message sizes.** Size of each struct in the compiler's own unit: 8-bit bytes on Arm, 16-bit words on the C28x. On the C28x an SPI driver normally puts each received byte in its own 16-bit word, so a struct laid over that buffer must have one word per wire byte; the Arm column is the wire size, and the two columns must match for the driver's cast to work. That one-byte-per-word layout is this repo's assumption: no C28x HAL was written and no buffer was tested.

| Struct | Arm (bytes on the wire) | C28x (16-bit words) |
|---|--:|--:|
| `TRX_TransactionHeader` | 4 | 4 |
| `TRX_TransactionFooter` (the CRC) | 2 | 1 |
| `TRX_Request_Header` | 2 | 1 |
| `TRX_Request_LastStatus` | 4 | 2 |
| `TRX_Phy` | 3 | 2 |
| `TRX_Request_CommandStore` | 48 | 32 |
| `TRX_Request_CommandSubmit` | 3 | 2 |
| `TRX_Request_CommandStop` | 4 | 3 |
| `TRX_Request_ConfigStore` | 8 | 6 |
| `TRX_PowerMode` | 3 | 2 |
| `TRX_DeviceConfigData` | 12 | 11 |
| `TRX_Request_CommandStore_Transmit_Params` | 16 | 12 |

Only the transaction header matches, and only in count: it is a union of a 32-bit view (two words on the C28x) and `uint8_t u8[4]` (four words), so its two views no longer cover the same bits. The driver builds each message by casting an SPI buffer to one of these structs and uses `sizeof` for lengths (`SPI_TRANSPORT_HEADER_LEN` is `sizeof(TRX_TransactionHeader)`). On the C28x a `uint16_t` field fills one word where the wire has two bytes, and bit fields pack into 16-bit units, so the layout in memory is not the layout on the wire.

**Byte order** is not the problem: the C28x and the Cortex-M cores are both little-endian. **The CRC** (CRC-16 CCITT-FALSE over the SPI block) is computed in the HAL, which was not compiled; a C28x HAL would have to feed it one byte per 16-bit word.

**The line.** The driver compiles for the C28x only with outside help, and then it is still wrong where it matters: 11 of 12 message structs differ in size from the bytes on the wire. **Tool or docs.** TI's host driver assumes a host with 8-bit bytes, and it says it can be ported, but a port to a C2000 would need a rewrite of how every message is packed and unpacked (estimate, not built), beyond a new HAL. Verdict for builders: to put a BP-CC1407P next to a C2000 today, use a small Arm host (a CC13xx LaunchPad development kit or an MSPM0) between the two, or write the byte packing yourself.

- Serialize each message into a byte buffer with explicit shifts and masks, one field at a time, and keep the C28x structs only as in-memory copies. The 12 structs above are the list to cover.
- Change the 15 event flags to `1UL << n` or `1ULL << n`; the driver already uses `1ULL` for its last four.
- Use the C28x's `__byte()` intrinsic, which reads and writes one byte inside a 16-bit word, for the SPI buffers.
- Put an MSPM0 between the C2000 and the radio, talking to the C2000 over SCI or SPI with a simple 16-bit protocol. MSPM0 is byte-addressed, so the driver's own code would apply there.
- Compile the TRX plug-in's own copy of the host driver, once downloaded, to see whether it differs from the Zephyr fork's.

**Ask.** Has anyone run a TI CC13xx or CC14xx transceiver host driver on a C2000? Is there a TI-supported way to pack messages on word-addressed cores?
