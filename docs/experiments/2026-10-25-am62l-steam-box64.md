# Does the Steam client run on the AM62L?

**Short answer.** The native arm64 client reaches its sign-in window with two small fixes (Second push, below). The x86 client under Box64 0.3.4 does not: it installs and stops before its login window. Inside a Debian trixie arm64 container, Box64 0.3.4 runs Valve's 32-bit bootstrap, which downloads and installs the client (504,927 kB in 436 s) and then the 64-bit client (424,455 kB in 357 s). Neither client draws a window. The 32-bit client stops on a missing C library call, and the 64-bit client restarts itself as the 32-bit one.

Terms: [vocab](../vocab.md). **Box64** runs x86-64 Linux programs on 64-bit Arm by translating their code; its **BOX32** mode runs 32-bit x86 programs. **binfmt_misc** is the kernel feature that lets Linux start a foreign binary through a translator automatically. **llvmpipe** is Mesa's software OpenGL. Scripts: `am62l-evm/steam/`; rows in `data/results/am62l-evm.csv` (variants `steam-*`). Checked 2026-10-25 on TI SDK 12.01 Linux (kernel 6.18.38), both A53 cores at 1.25 GHz, 2 GB RAM, no swap.

**Contents.** First try: the x86 client under Box64. Second push: the native arm64 client. Third push: a safer setup and what it costs. Fourth push: signed in, and Windows games through Proton on an ARMv8.0 core.

**Question.** How far does the x86 Steam client get on two A53 cores with no GPU: install, login window, store page, a light 2D game?

**Expectation.** Very slow or a stop before the store page: Steam's interface is a Chromium browser, and every instruction is translated on a 1.25 GHz in-order core.

**Result.**

| Step | What happened | Time | Whole-system RAM used |
|---|---|--:|--:|
| 32-bit bootstrap under BOX32 | runs; asks for its data link (`~/.steam/steam`) | 4 s | 637 MB |
| `steam.sh` with native `sh` | every x86 helper fails with `Exec format error` | 1 s | 623 MB |
| Bootstrap with the links made by hand | downloads, extracts and installs the client | 436 s | 952 MB |
| Its relaunch | goes through `/bin/sh`, `Exec format error` (no binfmt_misc) | | |
| 32-bit client started under BOX32 | `PltResolver32: Symbol __sched_cpualloc ... not found`, stops | | 629 MB |
| 64-bit client (`steamrt64/steam`) under Box64 | updates itself, verifies, then `Running steamrt64 client but not opted in. Re-starting the scout environment` | 357 s | 1,090 MB |
| `steam.sh` under an emulated x86-64 bash | the runtime checks abort in GLib (`g_module_open` not found), then the same 32-bit stop | 62 s | 586 MB |

The virtual screen stayed black in every screenshot. Installed size: 2,467 MB.

**What it does not show.** No login window, store page or game, so no frame rate.

**If you try it.** If you see `Exec format error` from `steam.sh`, the kernel cannot start x86 binaries by itself: `zcat /proc/config.gz | grep BINFMT_MISC`. Run the 32-bit bootstrap directly with `box64` and make `~/.steam/steam` point at its folder. If you see `__sched_cpualloc ... not found`, the Box64 build is too old for this Steam client.


## Second push: the native arm64 client

**Result.** Valve publishes an arm64 Linux client in its public beta channel (`steam_client_publicbeta_linuxarm64`, the same layout the UbuntuAsahi `steam-arm64` script uses). On the A53 it needs four changes, after which it updates itself and draws **Sign in to Steam** (account field, password field and QR code) between 20 and 43 s after start. No account was entered; that window is the stop point.

| Try | What happened | Cause | Fix |
|---|---|---|---|
| Client as downloaded (110 MB zip, 324 MB) | `Illegal instruction` at once | Built for ARMv8.1 LSE atomics (`ldaddal`, `swpa`, `cas`): 344 sites in `steam`, 1,711 in `steamwebhelper`, 5,882 in `steamclient.so`; the A53 is ARMv8.0 | `lse_trap.so` (below) |
| With `lse_trap.so` | `Failed to load steamui.so` | Valve's FFmpeg adds `av_malloc_tracked`, `av_mallocz_tracked`, `av_register_malloc`; stock FFmpeg 8 lacks them (Debian trixie has FFmpeg 7, testing has 9, Ubuntu 26.04 has 8) | `avshim.so`: the three calls on top of stock FFmpeg 8 |
| With both | Downloads a 670,648 kB update, installs it in about 6 minutes, restarts | expected | none |
| Restarted | `steamwebhelper` restarts every 10 s ("not responding", 64 restarts) | `steamwebhelper.sh` pins the browser to CPUs 2 to 6 (`taskset 0x7c`); the AM62L has CPUs 0 and 1 | drop the `taskset` |
| Browser starts | Client and browser die with `SIGBUS` in `memset` | CEF filled Docker's default 64 MB `/dev/shm` (158 MB in use once fixed) | `docker run --shm-size=512m` |
| Browser ready | "Unexpected Transport Error (0x3008)" dialog | The client checks its UI socket with `lsof`, absent from the container | install `lsof` |
| All fixes | **Sign in to Steam** drawn, 20 to 43 s after start | | |

Whole-system RAM in use with the sign-in window open: 1,180 to 1,330 MB of 1,960 MB (this includes the Doom framebuffer demo that kept running, about 500 MB of system baseline). The FFmpeg 8 container is Ubuntu 26.04; Mesa llvmpipe (LLVM 21.1.8); flags `-noverifyfiles -no-cef-sandbox -cef-disable-gpu -cef-disable-gpu-compositing`.

**The trap library.** `am62l-evm/steam/lse_trap/lse_trap.c` is an `LD_PRELOAD` library: a `SIGILL` handler decodes each LSE instruction (LD<op>, SWP, CAS, CASP, and LDAPR) and does the same operation with load-exclusive and store-exclusive, then steps past it. Atomics on unaligned addresses (legal with ARMv8.4 LSE2) run under one lock, and a `SIGBUS` handler covers unaligned LDAR and STLR. Its self-test (`test_lse.c`, built with `-march=armv8.1-a`) dies with `SIGILL` alone and prints PASS with the library: 2 threads, 1,000,000 increments each, 14.3 s, about 7 microseconds per trapped atomic. Any ARMv8.1 arm64 binary can run on an A53 this way, slowly.

**Other paths.** Box64 git has wrapped `__sched_cpualloc` for BOX32 since 2026-09-13 (after release 0.4.4), so a git build would pass the first stop of the x86 client; not built (the build host had no network, and the native client went first). The board runs 32-bit Arm programs (`CONFIG_COMPAT=y`; an `armhf` container reports `armhf`), so the Pi-Apps recipe (box86 for the 32-bit client plus box64) can run here. FEX-Emu still lists ARMv8.0 as supported but plans ARMv8.4 as its floor (FEX issue 4120).

**What it does not show.** No store page, library or game: those need a signed-in account. No frame rate. Speed of the trap path beyond startup.

**If you try it.** If you see `Illegal instruction` from `steamrtarm64/steam`, preload `lse_trap.so`. If you see `undefined symbol: av_malloc_tracked`, preload `avshim.so` on FFmpeg 8. If `steamwebhelper` restarts every 10 s, remove `taskset 0x7c` from `steamwebhelper.sh`. If the client dies with `SIGBUS` in `memset`, give the container `--shm-size=512m`. If you see "Unexpected Transport Error (0x3008)", install `lsof`. Scripts: `am62l-evm/steam/fetch_arm64.sh`, `setup_arm64.sh`, `run_arm64.sh` (`LSE_TRAP=1 AVSHIM=1`).

**Board state after the second push.** All Steam containers, images and files were removed (7.5 GB freed).


## Third push: a safer setup, and what it costs

**Result.** The client reaches a drawn **Sign in to Steam** page as an unprivileged user with Chromium's sandbox on, on Docker's default bridge network, with the scripts mounted read-only. Rewriting each LSE instruction after its first trap cuts trapped atomics at the idle sign-in page from about 2,280 per second to under 10, and time to the drawn page from 56 to 57 s to 46 to 49 s. What remains is the price of drawing a Chromium page in software: about half of one core while the page sits idle. Swap does not change it. Stop point: the sign-in page; no account is entered.

**Setup** (`am62l-evm/steam/setup_arm64_user.sh`, `run_user.sh`). Ubuntu 26.04 arm64 container, user `ubuntu` (uid 1000), `--init --shm-size=512m`, scripts at `/s` read-only, Steam's home at `/data`. Chromium's sandbox needs user namespaces: the kernel has `CONFIG_USER_NS=y` and `user.max_user_namespaces = 7770`, and Docker's default seccomp profile blocks `unshare(CLONE_NEWUSER)`, so this one container runs with `--security-opt seccomp=unconfined`. With that, `unshare -Ur` works as uid 1000, the renderer processes show `Seccomp: 2` (filter on) and the zygote runs in its own PID namespace; `-no-cef-sandbox` is no longer used. `--network host` is not needed.

**Hot-patching the atomics** (`lse_trap/lse_patch.h`, `LSE_PATCH=1`). At the first trap of each LSE instruction in a file-backed code page (never JIT code), the handler writes a stub for that exact instruction (its registers, size and operation) with `ldaxr`/`stlxr` (`ldaxp`/`stlxp` for CASP) into a code page within branch range, and turns the instruction into a branch to it. LDAPR becomes LDAR in place. MIN and MAX atomics, and sites first met on an unaligned address, stay on the trap path; a stub that later meets an unaligned address faults, and the SIGBUS handler undoes its pushes and emulates the instruction. Static patching of the files was not used: every client update replaces the binaries, and patching in memory leaves the files untouched. Check (`test_patch.c`: every patched form at 1 to 8 bytes, SP-relative base, flags across CAS, CASP, an aligned-then-unaligned site, a two-thread race): PASS 5 of 5 runs; one atomic add costs 6.7 to 6.9 microseconds trapped and 18 to 19 ns patched.

**Expectation.** Startup a few seconds faster (the earlier trap count was in the millions); idle CPU dominated by rendering, so little change there.

**Each mode to the drawn sign-in page** (one run each, two where shown; Doom kept running on HDMI outside the container through every run; "painted" is the first screenshot with over 1,000 colors; CPU is the container's cgroup time; board RAM is the highest `free` used during the run, 540 to 560 MB before it):

The two GPU flags cut idle CPU by about 40 percent. Big Picture draws its full-screen interface in software and needs 2.8 times as long. Over both swap runs 12 MB went to swap (3,107 pages out, 1,247 in): Steam to the sign-in page fits in the 2 GB.

**Limits.**

| Limit | Cause | Fixable here? |
|---|---|---|
| Every page is drawn in software; half a core at an idle sign-in page, 1.4 cores for Big Picture | no GPU driver for Chromium (Mesa llvmpipe or SwiftShader) | No. The GPU flags trim it by about 40 percent |
| Two in-order A53 cores at 1.25 GHz | the chip | No |
| About 0.6 to 1.0 GB of RAM for the client at the sign-in page, 0.4 to 0.7 GB left of 1.96 GB | Chromium plus the client | Partly: the lean flags; swap only helps cold pages |
| ARMv8.0: no LSE atomics | Valve builds for ARMv8.1 and newer | Yes: trap plus hot-patch; each site traps once (about 7 microseconds) |
| x86 games | need Box64 or FEX; FEX plans to drop ARMv8.0 | Partly; Box64 only |
| Sandbox needs `seccomp=unconfined` for the container | Docker's default profile blocks user namespaces | A custom profile that allows `unshare` would narrow it |
| Crash dumps go to Valve | the client's breakpad reporter uploads without asking | No switch found; keep `/dev/shm` empty between starts so it does not crash |
| A killed browser leaves its shared memory in `/dev/shm`; the next start dies with `SIGBUS` | Chromium cleanup | Yes: empty `/dev/shm` before a start (`modes_host.sh`) |

**What it does not show.** Anything past the sign-in page: store, library, a game, frame rate. One run per mode (two for trap, hot-patched and lean). Board RAM includes Xvfb and the Doom demo.

**If you try it.** If you see `undefined symbol: __atomic_compare_exchange_16` from a preload library, the library calls libatomic: write 16-byte atomics with `ldaxp`/`stlxp`. If every start after the first crashes with a minidump, empty `/dev/shm` in the container. If `unshare -Ur` fails as a normal user in the container, give that container `--security-opt seccomp=unconfined`.

## Fourth push (2026-10-27): signed in, and Valve's Windows path on an ARMv8.0 core

**Result so far.** Signed in, the arm64 client draws the store, downloads games and registers Valve's own arm64 tools for Windows games: FEX (Valve's x86 translator build), Steam Linux Runtime 4 and Proton Experimental. Valve's FEX does not run on the A53 as shipped. Rebuilt from the same commit for ARMv8.0, it runs x86-64 programs at once, and Proton's Wine processes start under it. Backyard Baseball '97 (the 1997 32-bit Windows program) starts, its `SteamAPI_Init` succeeds, and the arm64 client lists the game as Running and records play time. It quits about 10 s later without drawing a window: Wine's desktop process (explorer) is not ready within Wine's wait, so the game has no display driver. That is the stop point on 2026-10-27.

**Each stop and its fix.**

| Stop | Cause | Fix |
|---|---|---|
| Game exits at once, no message | Valve's `fex-compat-tool` is a Python script; the container had no `python3` | Install `python3` in the container |
| `RootFS path doesn't exist. This is required on AArch64 hosts` | Valve's arm64 SteamOS ships an x86-64 root file system at `/usr/share/guestos/fex-mesa`; a plain Linux has none | FEX's published Arch Linux image (1.36 GB download, 4.4 GB unpacked, 120 s plus 452 s on the board), linked at that path |
| FEX exits with code 4 (SIGILL) after about 110 s, no message | Valve's `FEX` binary holds 257 ARMv8.1 atomic instructions; the trap library catches them until FEX installs its own signal handler, then the first one kills the guest | Build FEX from Valve's commit (`37265b1`) with `-DTUNE_CPU=none -DTUNE_ARCH=armv8-a -DBUILD_FEXCONFIG=OFF -DBUILD_STEAM_SUPPORT=ON`, about 5 minutes on an Apple-silicon Mac mini in a Debian arm64 container; the 15 atomic sites left sit behind run-time CPU checks. `uname -m` under FEX: `x86_64` in under 1 s |
| `Failed to remap /proc/pid/cmdline data (prctl failed)` | Needs `CAP_SYS_RESOURCE` | Harmless; FEX goes on |
| First launch stays at Steam's "Launching" for over 25 minutes | Steam's `legacycompat/iscriptevaluator.exe` (an old game's install script) waits with almost no CPU (22 s in 26 min) | Skip it: start the game's exe through the same chain by hand (`am62l-evm/steam/run_proton.sh`) |
| `steamclient_init unable to load native steamclient library`, then an assertion in `lsteamclient` | This arm64 client ships only the arm64 `steamclient.so`; Proton's bridge needs the x86 one, and for a 32-bit game the 32-bit one, whose libraries `libopenal.so.1`, `libnm.so.0` and `libudev.so.1` are not in Steam Linux Runtime 4 | Link `~/.steam/sdk32` and `sdk64` to the x86 client's `ubuntu12_32` and `linux64` (left by the first try) and copy the three libraries from Valve's `steamrt3c` runtime into `ubuntu12_32`; the glibc loader log (`LDDBG=1` in `run_proton.sh`) names each missing one |
| `nodrv_CreateWindow: The explorer process failed to start` | Under FEX, Wine's explorer loads `winex11.drv` and is still starting when Wine stops waiting for it (about 30 s) | Second reading of the log: this line comes from Proton's wrapper process, not the game. The game process starts, loads `steam.dll`, prints one `lsteamclient` fixme and then logs nothing for ten minutes: it hangs in Steam API setup. The 32-bit `steamclient.so` in use is from the *stable* x86 client (2026-10-26) while the running client is the *public beta* arm64 build (version 1793056502); the bridge between them is version-matched. Next: fetch `steam_client_publicbeta_ubuntu12` at that version and use its `ubuntu12_32` instead |

**ScummVM, for comparison.** The same purchased Backyard Baseball '97 files load in ScummVM 2.9.0 (Debian) and in ScummVM built from source on 2026-10-27: the title screen and clubhouse draw full screen at 4:3, and both stop with an assertion in the SCUMM script stack (`_scummStackPos`) at Play Ball. The Steam files' `BASEBALL.HE0` (MD5 `b855daca2b7c40fc45592cdf5ce54f86`) is not in ScummVM's table, which lists a different Steam fingerprint for this game.
