# Can Linux run on one A53 core of the AM62L and Zephyr on the other, with no hypervisor?

**Short answer.** Yes, for a Zephyr hello world with a timer tick beside a booted Linux. U-Boot started Zephyr on core 1 with a PSCI `CPU_ON` call; Linux then booted on core 0 with `maxcpus=1 mem=1536M cpuidle.off=1`. Three minutes after Linux came up, `/sys/devices/system/cpu/online` read 0 and Linux read Zephyr's console ring at 0xEFFFF000 through `/dev/mem`: the head counter moved from 5,888 to 5,954 (bytes written) in 3 s and the last lines were `tick 269` and `tick 270`. The first version, with Zephyr in the on-chip SRAM, did not run, because Linux and TF-A use that SRAM. Terms: [vocab](../vocab.md). FAQ: [AM62L](../../am62l-evm/FAQ.md). 1 KB = 1,024 bytes.

**Question.** With Linux on A53 core 0, can a Zephyr image run on core 1 with no hypervisor, no remoteproc and no kernel module, and keep running while Linux is up?

**Vendor position.** TI ships a Jailhouse image for this board as its documented way to run an RTOS beside Linux. SDK download page: https://www.ti.com/tool/download/AM62L-LINUX-SDK/12.01.00.05.03. This run does not use it.

**What was tried.** 2026-10-22 between 10:55 and 11:30, on the AM62L evaluation module with an M4 Mac on UART0 (115200). Boot path: the micro-SD slot failed with the card on hand (U-Boot printed `Transfer data timeout`, and after a reseat `Card did not respond to voltage select! : -110`; the board's eMMC answered normally, so the card is the suspect). The board was booted over UART instead: SW3.4 ON, SW3.3 ON, SW3.2 ON, SW3.1 OFF (SW3.4 is the first row of the user guide's table; a full power cycle is needed, because the SW7 warm reset does not re-read the switches). The boot ROM sends `C` on UART0; `am62l-evm/tools/uart_boot.py` sent `tiboot3.bin` (XMODEM), `tispl.bin` and `u-boot.img` (YMODEM) from TI's Linux SDK 12.01.00.05.03 SD image, about 7 minutes to the U-Boot prompt. The SDK `.wic.xz` was written with `dd` to a 32 GB USB thumb drive on the Mac; U-Boot's `usb start` finds it, `load usb 0:2` reads the kernel (`Image-6.18.38-ti-00934-g8933766be737-dirty`) and `ti/k3-am62l3-evm.dtb`, and `booti` runs with `root=/dev/sda2`. Kernel to login prompt: about 30 s. A `usb start` after hot-plugging the stick into the running board hung U-Boot; a cold start with the stick already in works.

SRAM beside Linux was ruled out first. From Linux, `/dev/mem` shows WKUP SRAM at 0x707F0000 holding 34 KB of live code (TF-A's stub), and reads of MAIN SRAM above 0x70810000 raise a bus error (firewalled from the normal world); Linux's device tree claims 0x70800000 to 0x7080FFFF (`oc_sram`, with the SCMI mailbox at its start). So the SRAM images from the earlier plan were not used.

The DDR image (`build-ddr-core1`, `am62l-evm/zephyr/core1-ddr.overlay` plus `core1-ddr.conf`): Zephyr a915b2f, `apps/core1-hello`, linked at 0xE0000000 in a 256 MB DDR region, entry 0xE00008BC, `zephyr.bin` 44.0 kB (sha256 6543a9a3fa6233850a789302c08976b47ac75688649a8705d74d8a9073dc0778). It contains no PSCI, SCMI or SMC code, leaves the GIC distributor untouched (`am62l-evm/zephyr/patches/gic-skip-distributor.patch`) and writes its console to a 4 KB ring at 0xEFFFF000. The start, in U-Boot: `load usb 0:2 0xE0000000 /boot/zephyr-core1.bin`, then `am62l-evm/tools/psci_stub.py` writes a 7- or 8-instruction AArch64 stub with `mw.l` and runs it with `go`.

**How far it got.** Configure, build, load, run and verified. The stub got PSCI_VERSION 0x10001 (PSCI 1.1), AFFINITY_INFO for core 1 returned 1 (off), CPU_ON(MPIDR 0x1, 0xE00008BC) returned 0, and AFFINITY_INFO then returned 0 (on). The ring, read with `md` in U-Boot, held `*** Booting Zephyr OS build a915b2f12675 ***`, `core1-hello: MPIDR_EL1=0x80000001 (Aff0=1) CurrentEL=EL1`, then `tick 0`, `tick 1`, `tick 2`. So TF-A starts a secondary core at non-secure EL1 on this build, which answers the open question left by the earlier SRAM image. Linux then booted on core 0 with `maxcpus=1 mem=1536M cpuidle.off=1` (`Memory: 1450680K/1572864K available`). The ring lies outside Linux's memory, so `/dev/mem` allowed the read: magic 0x52524C46, head 5,888 then 5,954 (bytes written) 3 s later, last lines `tick 269` and `tick 270`. `dmesg` shows no SError, Oops or stall.

**The line.** No stop. The numbers: Zephyr 44.0 kB in DDR, one core, EL1 non-secure, started by PSCI; Linux on the other core with 1,536 MB, no hypervisor, no remoteproc, no kernel module. What the run does not show: any interrupt beyond Zephyr's own timer, any shared peripheral, Zephyr surviving Linux's cpuidle (it was turned off), a Linux reboot while Zephyr runs, Zephyr in SRAM beside Linux (the SRAM is not available), and any timing or power figure. Zephyr was started from U-Boot, not by Linux, so this does not show Linux starting or stopping the RTOS.

**Ask.** If you know whether TF-A on the AM62L reserves or relocates the WKUP SRAM stub, or which firewall setting opens MAIN SRAM above 0x70810000 to the normal world, say where it is documented.
