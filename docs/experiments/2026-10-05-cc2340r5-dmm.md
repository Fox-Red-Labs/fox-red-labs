# Can the TI LP-EM-CC2340R5 run Bluetooth and an 802.15.4 radio stack at the same time?

**Short answer.** Not with TI's example on this chip: it compiles, then is 2.1 kB short of the chip's free RAM even before its heap. The same build links, but has not been run, on the 64 kB CC2340R53.

Terms: [vocab](../vocab.md) (DMM, 802.15.4, heap, .bss, linker). Errors and fixes: [CC2340R5 FAQ](../../cc2340r5/FAQ.md). 1 kB = 1,024 bytes.

**Question.** TI's larger CC27xx chips can run Bluetooth plus Zigbee, Thread or TI 15.4 at once, using TI's Dynamic Multi-protocol Manager (DMM). Can the CC2340R52 chip on this board?

**Vendor position.** The DMM release notes in the F3 SDK 9.21.00.36 (`docs/dmm/release_notes_dmm_1_00_00.html`): "The CC23XX products do not support DMM." No reason given.

**What was tried.** On an Intel Mac with macOS 15.7.9, 2026-10-05, TI's DMM example for the CC2755P10 board was moved to this board. The example is `examples/rtos/LP_EM_CC2755P10/dmm/mac_sensor_ble_basic`: Bluetooth plus TI's 15.4 MAC sensor. Expected: lighter than Bluetooth plus Zigbee. Changes: board set to LP_EM_CC2340R5. A CC27xx-only security key store removed. Two flash storage addresses moved inside 512 kB. Compiler flags changed from Cortex-M33 to Cortex-M0+. The CC23xx Zigbee linker file used. Diffs: `cc2340r5/matrix/dmm_cc23*.diff`, linker file `dmm_r53_linker.cmd`. TI Arm Clang 5.1.1, SysConfig 1.26.3.

**How far it got.**

- SysConfig accepted the DMM module for the CC2340R5 and generated a full configuration.
- TI ships the DMM library already built for this core (`source/ti/dmm/libraries/default/lib/ticlang/m0p/dmm_library.a`).
- Everything compiled.
- Link on the CC2340R52, which has 36 kB of RAM: failed, with `error #10099-D: program will not fit into available memory, or the section contains a call site that requires a trampoline that can't be generated for this section, or the section contains padded functions. run placement with alignment fails for section ".bss" size 0xca0e.` The linker then listed `SRAM size: 0x9000 unused: 0x7444 max hole: 0x70b0`. The zero-initialized data needs 50.5 kB (0xca0e), which includes the 19.3 kB heap the example sets for this chip. Free RAM: 29.1 kB in total, 28.2 kB in the largest block.
- Link on the 64 kB CC2340R53: passed, after cutting the heap TI's example sets for that chip from 40 kB to 24 kB. Flash 255 kB; RAM 62.1 kB of 64 kB. TI's own example configuration already has a branch for `LP_EM_CC2340R53`.
- Not run: there is no CC2340R53 board on this bench.

**The line.** The link step, on RAM. **Unknown (suspected: Chip limit).** Without the heap, the two stacks still require 31.2 kB: 2.1 kB more than the chip's 29.1 kB free, and 3 kB more than its largest free block. Only TI's example was tried, moved by hand. On the CC2340R53 it links with 1.9 kB unused. Whether a 24 kB heap is enough at run time is unknown.

- Run it on an LP-EM-CC2340R53.
- Find the smallest heap that survives a Bluetooth connection plus 15.4 traffic.
- Pair Bluetooth with Zigbee instead of the MAC sensor. Expected: it needs more RAM; not measured.
- Cut Bluetooth to broadcast only.

**Ask.** Is "not supported" here a RAM statement or something deeper in the scheduler? Has anyone run DMM on a CC2340R53?
