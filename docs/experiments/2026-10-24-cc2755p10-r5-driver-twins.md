# Do the TI Drivers examples built from the CC2340R5 source run on the LP-EM-CC2755P10?

**Short answer.** Yes. All 33 shared F3 SDK examples, built with the LP-EM-CC2340R5 `.c` files inside the LP-EM-CC2755P10 project, flashed and ran with no fault. 22 matched TI's README on the board, 10 stopped at missing hardware (SD card, I2C sensor, second board, input signal) with the message TI documents, and the `pwmled1` fade could not be seen.

Terms: [vocab](../vocab.md). FAQ: [LP-EM-CC2755P10](../../cc2755p10/FAQ.md). An earlier build-only check found the app source byte-identical for the two boards. Checked 2026-10-24, F3 SDK 9.21.00.36, TI Arm Clang 5.1.1.LTS, SysConfig 1.28.0, UniFlash 9.6.0, one LP-EM-CC2755P10 on an LP-XDS110.

**Question.** That check said the twins should work because only SysConfig and the linker file differ. Do they behave like TI's own examples on the chip?

**Setup.** Each image was flashed with DSLite without a chip erase, after a check that its CCFG and SCFG equal the board's known-good files. The backchannel UART was held open at 115200 baud, text was sent where the example asks for input, and GPIO DOUT was read four times with the debugger.

**Expectation.** TI's README text for each example (LED on after init, LED toggling each second, UART banner, echo, AES and SHA output).

**Result.** 33 of 33 ran without a fault. AES-CBC and AES-ECB ciphertexts equal an independent library's; SHA-256 of "1" is correct; empty and watchdog toggle DIO16; the UART echo returns `abc`; the ADC, temperature and NVS examples print plausible values. The `log` example prints at 3,000,000 baud, not 115200.

**The line.** None. The ten examples that wait need the other end of a bus or a card; the UART and pin checks do not tell whether those paths work. Button presses were not run.

**Ask.** A second board (for SPI and I2C pairs) and an SD card would close the ten.
