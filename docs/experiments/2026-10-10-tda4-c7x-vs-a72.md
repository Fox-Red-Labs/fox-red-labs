# How much faster is the SK-TDA4VM's C7x and MMA than its two Cortex-A72 cores when a TI model-zoo network runs on the CPU instead?

Terms used here are in [docs/vocab.md](../vocab.md) (Cortex-A72, C7x, MMA, TIDL, execution provider, fp32 and int8, the model zoo and its name prefixes) and the board's [FAQ](../../tda4/FAQ.md). Board page: [tda4/README.md](../../tda4/README.md). Numbers: `dl_inference_ms` rows in `data/results/tda4.csv`.

**Short answer.** On the SK-TDA4VM, eight TI model-zoo networks ran 13 to 135 times faster on the C7x DSP with its MMA accelerator than on the two Cortex-A72 cores: 2.9 ms against 37 ms for the smallest, 13.8 ms against 1,767 ms for the pose model. The CPU ran the zoo's fp32 graphs and the accelerator its int8 artifacts, so the ratio is what a developer pays when a model falls back to the CPU on this image, not a like-for-like comparison of the two cores; timing only, outputs not compared.

**Question.** TI's SK-TDA4VM has two general-purpose Cortex-A72 cores and a C7x DSP with a matrix accelerator (MMA) that TI rates at 8 TOPS. If a model runs on the accelerator, how much time does it save against running the same model on the Arm cores, and does the saving depend on the model's size?

**Vendor position.** TI, SK-TDA4VM product page and the TDA4VM data sheet (read 2026-10-09): "C7x floating point, vector DSP, up to 1.0 GHz, 80 GFLOPS, 256 GOPS" with a "Deep-learning matrix multiply accelerator (MMA), up to 8 TOPS (8b) at 1.0 GHz". TI's Edge AI model-zoo page lists inference times on the C7x for four models (2.03 ms MobileNetV1 mlperf, 3.04 ms regNetx-200mf, 5.03 ms yolox-nano-lite 416, 5.9 ms ssdLite mobDet 320, read 2026-10-09). TI publishes no CPU-only figures for these models, and the zoo ships them compiled for the accelerator only.

This repo's expectation before the run: "10 to 100 times on convolutional models; less on tiny ones where the call overhead dominates".

**What was tried.** Board: SK-TDA4VM (J721EXSKG01EVM, PROC112A1), TI Edge AI SDK 11.00.00.08, Linux 6.12.17-ti, onnxruntime 1.15.0, no display, no Ethernet, everything over the serial console, 2026-10-09 to 10.

1. Accelerator: each ONNX and TFLite model in `/opt/model_zoo` through ONNX Runtime or TFLite with TI's TIDL delegate, using the zoo's precompiled int8 artifacts. Random input, one warm-up, 30 timed runs, median wall time in Python. The runtime's log confirmed every node went to the C7x (274 of 274 for the pose model).
2. CPU: the same ONNX files through ONNX Runtime's CPU execution provider with two threads, one per A72, as the zoo ships them: fp32 graphs, not quantized for a CPU. Random input, one warm-up, three timed runs, median.
3. The three TVM models in the zoo through the DLR runtime (2026-10-10) on the accelerator only; the zoo holds no CPU build of them.

**How far it got.** Measured, timing only. All 14 zoo models ran on the accelerator; the 8 that have an ONNX file also ran on the Arm cores. The CPU runs on the detection models print ONNX Runtime's warning `execution_frame.cc:857 VerifyOutputSizes] Expected shape from model of {51} does not match actual shape of {200} for output labels`; whether the two sides return identical outputs, only how long each took.

Accelerator only (no CPU build in the zoo): TFL-CL-0000 MobileNetV1 2.17 ms, TFL-OD-2020 ssdLite mobDet 320 6.40 ms, TFL-SS-2580 deeplabv3 mobv2 12.11 ms, TVM-CL-3090 MobileNetV2 2.93 ms, TVM-OD-5120 ssdLite mobDet 320 12.97 ms, TVM-SS-5710 deeplabv3lite cocoseg21 8.85 ms. TI's four published figures are within 10 percent of the values measured here. The TVM build of ssdLite mobDet 320 (DLR 1.13.0 runtime, fp32 NHWC input) is 12.97 ms against 6.40 ms for the TFLite build of the same network (TFLite runtime, uint8 input; the TFLite runtime's version was not recorded). Two things differ, the runtime and the input format, and they were not tested apart: **Unknown (suspected: the input conversion inside the graph).**

**The line.** No line was reached: everything ran. The result is the shape of the ratio.

The ratio grows with the model. The smallest network (regNetx-200mf; the name says about 200M floating-point operations per image) gains 13x; the three 640x640 YOLOX-s networks gain 128x to 135x. On the accelerator the big models take only 4 to 5 times longer than the small one (13.8 ms against 2.9 ms), while on the CPU they take 40 to 50 times longer (1,767 ms against 37 ms). Suspected, not profiled: the accelerator's time has a floor of a few milliseconds that does not shrink with the model (loading the input, running the graph through the runtime, reading the output back), while the CPU's time grows with the arithmetic. No operations were counted, so this is the shape of the table, not a measurement of either.

What the ratio is not. The CPU ran fp32 graphs through a generic runtime; the accelerator ran int8 artifacts TI compiled for it. An int8 CPU build with Arm's optimized kernels would probably cut the CPU time, by how much was not measured (an estimate, nothing built), and the zoo ships none. So these numbers measure what a developer sees on this image when a model falls back to the CPU (for example because an operator is not supported by TIDL), not the two cores' arithmetic against each other.
