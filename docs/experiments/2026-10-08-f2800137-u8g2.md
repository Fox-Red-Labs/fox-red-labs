# Does the u8g2 display library compile for a TI C2000 LaunchPad (LAUNCHXL-F2800137), where a byte is 16 bits?

**Short answer.** Yes, with one line of your own: u8g2 2.37.1, the common library for small monochrome displays, compiles and links for the C28x with no change to its files once `uint8_t` is defined as `unsigned char`. A test program with u8x8 text and one u8g2 font for a 128x64 SSD1306 display takes 19 kB of flash and 8.3 kB of RAM. Two catches: the C2000 compiler has no `uint8_t` of its own, and if you take C2000Ware's (`uint16_t`), both fonts tried fail with `error #145`. Fonts and the frame buffer take twice the memory. Compile and link check only, on a Mac; not run on a display.

Terms: [vocab](../vocab.md) (C2000 and C28x, u8g2 and u8x8, SSD1306, link). Errors and fixes: [LAUNCHXL-F2800137 FAQ](../../c2000-launchpad/FAQ.md#libraries-written-for-8-bit-bytes). 1 kB = 1,024 bytes. Checked 2026-10-08 on macOS 15.7 (Intel) with TI's C2000 compiler 25.11.1.LTS.

**Question.** u8g2 is a widely used C library for small monochrome OLED and LCD screens, in Arduino sketches and plain C. Its code and fonts are written in terms of 8-bit bytes. Does it build for a chip that has no 8-bit type?

**Vendor position.** The C2000 compiler's `stdint.h` defines `uint8_t` only for byte-addressed targets (MSP430, C55x byte mode, C6000, Arm, PRU, C7000, C29), not for the C28x. C2000Ware's driverlib defines one for its own use: `typedef uint16_t uint8_t;` in `driverlib/f280013x/driverlib/inc/hw_types.h`, under the comment "Definition of 8 bit types for USB Driver code to maintain portability between byte and word addressable cores of C2000 Devices." On the C28x, `char` is 16 bits (`docs/vocab.md`, C2000). u8g2's own documentation was not checked for 16-bit `char`.

**What was tried.**

- **u8g2 2.37.1** (commit `414efcd`, BSD 2-clause), fetched by `third-party/u8g2/fetch.sh`: the core u8x8 and u8g2 files, the SSD1306 128x64 driver, and two fonts copied out of upstream's font files unchanged (`u8x8_font_chroma48medium8_r` for u8x8 text, `u8g2_font_6x10_tr` for u8g2). No u8g2 file was edited.
- **This repo's test program**, `c2000-launchpad/compile-checks/u8g2/u8g2_check.c`: u8x8 draws "Hello C28x" in the 8x8 font; u8g2 clears a full frame buffer, draws the same text in the 6x10 font and sends the frame. The byte callback stores each byte it would send in an array, so no I2C or SPI peripheral is involved.
- **Compiler and link.** `cl2000 -v28 -ml -mt --float_support=fpu32 --abi=eabi --opt_level=2 --c99`, linked with this repo's F2800137 flash layout and a 1,024-word stack. Three ways to get `uint8_t`: none (the compiler's own `stdint.h`); C2000Ware's `uint16_t`; and `unsigned char`, which is also 16 bits on the C28x.
- **Host emulation.** The same program built twice with the Mac's clang, with `uint8_t` 8 bits and then widened to 16 bits, and the bytes each sends compared; both builds take the two fonts as brace lists of numbers, because a string cannot fill a 16-bit array. This tests only whether u8g2 relies on 8-bit wraparound. It is not the C28x: `int` stays 32 bits on the Mac.

The link leaves out two compiled files, `u8g2_d_setup` and `u8g2_d_memory`, because they reference every display and buffer u8g2 supports; the test program's own setup covers the one SSD1306 128x64 display, so the sizes below are for that display only. The six warnings in the last build are five upstream files without a final newline and the linker's note that the entry point is `code_start`, not `_c_int00`.

**1. No `uint8_t`.** `"csrc/u8x8.h", line 215: error #20: identifier "uint8_t" is undefined`, then 2,701 more that follow from it (1,350 of them `error #91: function returning function is not allowed`); all of them go away once `uint8_t` is defined. **Chip limit.** The C28x cannot address a single byte, so its compiler has no exact 8-bit type. Define one before u8g2's headers.

**2. C2000Ware's `uint8_t` breaks the fonts.** `"extract/fonts_extract.c", line 11: error #145: a value of type "char [772]" cannot be used to initialize an entity of type "const uint8_t [772]"`, the same for the 979-byte font, then `error #10234-D: unresolved symbols remain` for both fonts at link. **Third-party behavior.** u8g2 stores both fonts compiled here as string literals, and C lets a string fill only an array of a character type; `uint16_t` is `unsigned int`. So does every other font in u8g2 2.37.1: all 2,043 in `u8g2_fonts.c` and all 131 in `u8x8_fonts.c` are string literals (counted in the upstream files), so the same error is expected from any of them; only these two were compiled. With `unsigned char`, which is 16 bits wide here, the fonts compile. **Tool or docs.** The `uint16_t` version comes from C2000Ware, whose comment says it is for its USB driver code, and nothing warns that it breaks string data. A C2000Ware project that includes `driverlib.h` gets the `uint16_t` version, so keep u8g2's files out of driverlib's reach (a separate file for the display code) or convert the fonts to brace lists.

**3. Memory, from the map** (the linker map). Flash 9.7k words (19 kB): 9,674 in `FLASH_MAIN`, 28 in `FLASH_BOOT`, 2 at `BEGIN`. RAM 4.3k words (8.3 kB), of which this repo's byte capture array is 2k words, the frame buffer 1,024 and the stack 1,024. Each font byte takes a word: `u8g2_font_6x10_tr` is 979 words (1.9 kB) where a byte-addressed chip stores 979 bytes, and the 128x64 frame buffer is 2 kB instead of 1 kB.

**4. Wraparound, host emulation.** Both builds sent the same 1.3 kB (each build prints `uint8_t is 8 bits` or `uint8_t is 16 bits` to confirm which it was). For this program's calls, u8g2 does not depend on a byte rolling over at 256. Other drawing calls, other fonts and 16-bit `int` were not covered.

**The line.** No line reached. It compiles and links; the screen does not draw. The one rule for builders: give u8g2 `unsigned char` as its `uint8_t`, not C2000Ware's `uint16_t`, and budget twice the bytes for fonts and the frame buffer.

- Run it: an SSD1306 on the F2800137's I2C pins with u8x8's hardware I2C callback, then compare the bytes on the bus with the host emulation's 1,356.
- Use the page buffer (`_1` setup, 128 bytes) instead of the full frame to save 896 words of RAM.
- Pack two font bytes per word with the `__byte()` intrinsic to halve font flash; that needs a change to u8g2's font reader.
- Check 16-bit `int` paths: large coordinates, `u8g2_uint_t` set to 16 bits, and the circle and line code.

**Ask.** Has anyone run u8g2 on a C2000? Did any drawing call misbehave where a byte would wrap at 256?
