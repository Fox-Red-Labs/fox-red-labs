# Does ESPHome's Zigbee device run on the TI LP-EM-CC2755P10, and what does it leave free?

**Short answer.** Yes. A normal ESPHome YAML (one switch on the LED, one chip-temperature sensor, Zigbee router, no logger, no Wi-Fi) produced C++ that builds with TI's compiler, FreeRTOS and the ZBOSS Zigbee stack libraries (ZBOSS is the Zigbee stack in TI's SDK for this chip) for the LP-EM-CC2755P10 after a 388-line shim was added and changed no ESPHome file. Flashed, it joined the house Zigbee network (ZHA, Home Assistant's Zigbee integration) within 8 s, showed up with a switch and a chip-temperature sensor, switched the red LED 20 of 20 times from Home Assistant at a median of 87 ms, and reported 21 C every 30 s. The image is 263 kB of flash and 37.6 kB of RAM, so 124.4 kB of the chip's 162 kB of RAM is free (127.4k bytes, against the 130k expected).

Terms: [vocab](../vocab.md). 1 kB = 1,024 bytes. A router relays Zigbee traffic and stays awake; an end device sleeps and talks to a router. SysConfig is TI's settings tool. ZHA is Home Assistant's Zigbee integration. `-Oz` is the compiler's smallest-size setting. ESPHome turns a YAML file into firmware; ZBOSS is the Zigbee stack both ESPHome's Zigbee component and TI's Zigbee examples are written against. "Link" means the program was assembled into one image with no missing pieces.

**Question.** Does ESPHome's Zigbee layer (ZBOSS calls) fit and link on TI's Zigbee stack with room for ESPHome's core?

**Vendor position.** ESPHome's Zigbee component supports switches and numbers only on its nRF52 platform, where it calls Nordic's build of ZBOSS (`zboss_api.h`, `zigbee_enable()`, `zigbee_default_signal_handler()`); its ESP32 version is a different file set on Espressif's library. ESPHome has no TI platform, as the component sources installed with ESPHome 2026.9.1 show, read 2026-10-13. TI ships ZBOSS R23 as prebuilt libraries for the Cortex-M33 (`third_party/zigbee/libraries/zboss_r23/*/lib/ticlang/m33f`, F3 SDK 9.21.00.36) and one Zigbee example per board, `onoff_light`, built with a makefile, FreeRTOS and a SysConfig file. Neither says anything about the other.

**What was expected, written down before the build** (2026-10-05 and 2026-10-07): the Zigbee calls are the same stack, so the work is everything around them; about 130 kB of RAM left beside the Zigbee router (TI's own example uses 36 kB of the 162 kB); and a blocker in porting ESPHome's core to FreeRTOS.

**What was tried.**

1. `ports/esphome-ti/frl-esphome-fit.yaml` on ESPHome's nrf52 platform, the template, because it is the only one whose Zigbee component offers a switch. `esphome compile --only-generate` made the C++ in 0.54 s: 115 files, 960 kB; its Zigbee folder has 17 files, 11 of them for nRF52. The tree was kept.
2. Every ZBOSS and platform name the generated code and the Zigbee component use (225 names) was listed and looked up in TI's headers and in the symbols of TI's prebuilt libraries.
3. Builds: TI's `onoff_light` unmodified for the baseline, then three variants, then a build that compiles ESPHome's core, switch, sensor and GPIO switch components, its Zigbee component and the shim with TI's flags, and links them as TI's makefile does. `ports/esphome-ti/build.sh` reproduces it from the YAML: LINK_OK in 62 s on the Mac, same bytes.

The 225 names:

| Group | Names | Where they come from |
|---|---|---|
| ZBOSS calls and macros TI also has | 127 | `zb_get_app_signal`, `zb_buf_free`, `ZB_ZCL_SET_ATTRIBUTE`, `zb_zcl_add_cluster_handlers`, `ZB_AF_REGISTER_DEVICE_CTX`, `zb_get_short_address` and the rest; every one is in TI's R23 headers |
| Defined by ESPHome itself | 42 | The Binary Output and Analog Output clusters TI's R23 headers have neither; ESPHome writes its own attribute lists and handlers, so nothing is missing |
| Generated names | 37 | The component objects and attribute structs in `main.cpp` |
| Nordic or Zephyr only | 15 | `zigbee_enable`, `zigbee_default_signal_handler`, `zigbee_configure_sleepy_behavior`, `ieee_addr_to_str`, `zb_error_to_string_get`, `settings_load`, `settings_subsys_init`, three `flash_area_*`, two partition ids, three header names |
| Not in TI | 4 | `zb_zcl_basic_attrs_ext_t` (struct), `ZBOSS_DECLARE_DEVICE_CTX_EP_VA` (macro), the two cluster name stems |

The 15 Nordic names are the real gap, and they are what the shim writes.

**How far it got.** Verified on the board (next section). The build steps, in order, with what stopped each:

| Step | Result | Cause tag | What fixed it |
|---|---|---|---|
| C++ compile of ESPHome with TI's include path | `<cerrno> tried including <errno.h> but didn't find libc++'s <errno.h>` | Tool or docs | TI's POSIX `errno.h` directory sat ahead of the toolchain's. Put it last (`-idirafter`) for C++ files |
| C++ compile, `strings.h` | `cannot initialize return object of type 'char *' with an rvalue of type 'const char *'` (`index`, `rindex`) | Tool or docs | TI Arm Clang 5.1.1's inline `index()` is not valid C++ at -Oz. `-U_INLINE` for C++ files |
| ESPHome's header names | The port's `hal.h` was never picked; ESPHome's own was | Our mistake | Quote includes look in the including file's folder first. Copy the generated tree and lay the shim headers over it |
| Register reads in C++ | `field has incomplete type 'serialRomBldrParam_t'` in TI's `hw_fcfg.h` | Tool or docs | The driverlib header declares a struct inside a union and is not valid C++. The three register reads (MAC address, reset, die temperature) are in one C file |
| Link | `fatal error: invalid option: --wrap=zb_zcl_put_reporting_info_from_req` | Tool or docs | TI's linker (`tiarmlnk`) has no `--wrap`. ESPHome uses it for four debug-only hooks; dropped, and the three radio ones stubbed |
| Link | `symbol "malloc" redefined` | Our mistake | TI's FreeRTOS setup already routes `malloc` to its heap. The port's copy was removed; `new` and `delete` follow |
| Link | LINK_OK, but 47.6 kB of RAM | Our mistake | TI's `zb_mem_config_lprf3.h` had been left out, so ZBOSS's tables were at their large default (+14.1 kB). Included, as TI's example does |

Each error above has an entry with the fix in the [CC2755P10 FAQ](../../cc2755p10/FAQ.md#building-c-esphome-with-tis-zigbee-flags).

**On the board.** The board sat on its standalone LP-XDS110 probe. Main flash (0 to 0xE8000), the configuration area (CCFG) and the security configuration (SCFG) were read twice, identical both times. The board was then flashed with UniFlash's `dslite --mode flash -e -f` and the backup restored at the end (read back identical). Before the flash, the image's CCFG and SCFG were checked equal to TI's example.

| Check | Result | How checked |
|---|---|---|
| Join | Listed in ZHA within 8 s of the flash finishing, twice (second after removing it from ZHA: about 7 s); LQI 136, RSSI -66 dBm; entities: switch, chip temperature, signal, link quality, identify button | ZHA device list, polled every 3 to 4 s |
| 20 switch commands | 20 of 20, state settled in a median of 87 ms (68 to 279); a second run of 20: median 90 ms | Home Assistant entity state |
| LED | 8 of 8 commands matched the LED pin (DIO16) read from the chip with the debugger, on and off | pin read |
| Temperature | 21.4, 21.3, 20.9, 21.3 C at 30 s spacing after the second flash; the first image reported 340 and 331 because the shim missed that TI's call returns degrees times 16 | Home Assistant sensor; not compared with a second thermometer |

Both joins used a factory-new chip (the flash erases the Zigbee settings).

**The line.** Nothing stopped the link or the run, so there is no limit to report. The numbers are static, from the linker map, in bytes (the chip has 165.9k bytes of RAM, 162 kB, and its application flash region is 904 kB):

| Build | Flash | RAM | RAM left |
|---|---|---|---|
| TI `onoff_light` as shipped (a coordinator, logging on) | 280,814 | 36,386 | 129,502 |
| Same example as a router, logging on | 265,878 | 36,158 | 129,730 |
| Router, logging off (the baseline for ESPHome) | 259,128 | 31,013 | 134,875 |
| ESPHome + Zigbee router + shim, TI's heap size | 269,384 | 34,376 | 131,512 |
| Same, heap +4 kB and a 2 kB ESPHome task stack | 269,384 | 38,472 | 127,416 |
| TI `onoff_light` as an end device, logging off | 206,203 | 25,524 | 140,364 |
| ESPHome + Zigbee end device + shim, heap +4 kB | 216,172 | 32,976 | 132,912 |

ESPHome's core, scheduler, switch, sensor and Zigbee component add 10.0 kB of flash and 3.3 kB of static RAM to TI's router with logging off; 7.3 kB of RAM once the heap and task stack ESPHome needs are counted. The 4 kB of extra heap is an estimate (the heap array grows by 4 kB to hold ESPHome's allocations and its 2 kB stack); the run on the board below shows the used amount only through the join and toggles; heap use was not read. The router's RAM is 23 percent of the chip's; its flash is 29 percent of the application region. As an end device (ESPHome's default role, `router: false`), the same YAML is 211 kB of flash and 32.2 kB of RAM, 129.8 kB free.

The shim, all of it: 126 lines to start ZBOSS and ESPHome's loop on two tasks and answer the 15 Nordic calls; 119 lines of platform code (clock, mutex, wake, two LED pins, a temperature read, preferences stubbed); a 20-line C file; 123 lines of headers. ESPHome's generated files are not edited.

**What this means.** The Zigbee layer needs no change to ESPHome's files on this chip; the start-up code in the shim, written from TI's example, worked on the first flash. What it does not show is what the link cannot show: join a network, answer a switch command, send a temperature report.

**What this does not establish.** Two joins and 20 toggles on one board on one day. No long run: availability over hours, a power cycle, and the heap ESPHome uses at run time (4 kB was added and not measured) are not checked. The random bytes and preferences are stubs, so ESPHome's saved settings do not survive a reset (ZBOSS's own network settings do). Two things are lost against the Nordic build: ESPHome's radio sleep-time counters (TI's libraries export no `zb_trans_*` calls to wrap) and its reporting-info debug line. The temperature is not checked against a second thermometer.

**Ask.** Whether the Binary Output and Analog Output clusters are meant to be absent from TI's ZBOSS R23 headers, and whether anyone else has built ESPHome's Zigbee component on TI's ZBOSS libraries, are not answered in TI's public documentation.

**Effort.** 16 minutes from the first command to the first link, about 25 minutes to the final numbers (the repeat link from the saved script took 62 s), and about 10 minutes for the flash, the join and the tests. One rebuild fixed the temperature scale.

**Verdict.** 127 of the 131 ZBOSS names the code needs were already in TI's headers. The other four each cost one build to find: a POSIX header, an inline function, a driverlib header and a linker flag. Nothing needed forking, and it ran on the first flash.
