# Does a compile shim get TI's CC1407P host driver running on the LAUNCHXL-F2800137?

**Short answer.** The shim fixes the build and nothing else. The driver then builds a different first message than an Arm core does. With `portability/cc1407p-host/c28x/c28x_compat.h` the 7 driver files, the bare HAL and a bench program compile and link with 0 errors and run on the LAUNCHXL-F2800137. So the driver still needs a field-by-field message packer for 16-bit-char chips. No radio was attached; the radio was a fake that answers every transfer with zeros.

Terms: [vocab](../vocab.md). Follows [E73](2026-10-08-f2800137-cc1407p-host-driver.md), which only compiled. Code, results table and causes: `portability/cc1407p-host/c28x/README.md`. Checked 2026-10-24 on macOS 15.7 (Intel), C2000 compiler 25.11.1.LTS, C2000Ware 26.02.00.00 LTS, probe <probe serial>.

**Question.** E73 found 524 errors as shipped and said all 7 files compile with C2000Ware's `uint8_t` and the packed attribute defined away. Is that the whole fix, and what does the driver do when it runs?

**Setup.**

- Shim: `--preinclude=c28x_compat.h` (16-bit `unsigned char` as `uint8_t`, empty `__packed__`). TI's files are untouched.
- Image: TI's driver, `hal_bare.c`, a fake-radio glue file and a bench program, RAM load, `-O2`.
- Reference: the same files built with clang on a Mac, where a byte is 8 bits.
- Run: load over the onboard XDS110, run to the breakpoint at `bench_done`, read the result variables. Twice, identical.

**Expectation.** From E73: struct sizes differ, so the first message differs; the CRC routine, which takes a byte array, matches.

**Result.**

| Check | PC reference | F2800137 |
|---|---|---|
| Files that compile without the shim | | 1 of 12 (the startup assembly); 750 errors |
| Files that compile with the shim | | 12 of 12, 0 errors, 51 warnings |
| Flash, RAM | | 8.4 kB, 8.7 kB (stack used 86 of 1k words) |
| CRC-16 of `123456789` | 0x29B1 | 0x29B1 |
| First SPI message | `00 04 11 00 02 32 00 00 E9 71` (10 bytes) | `00 11 00 00 01 00 00 00 C8` (9 units) |

The message differs in length, in the length byte, in the request number (0x32, CONFIG_LIST, is missing) and in the CRC. `TRX_Host_open` waits for the radio's answer and never returns, so the bench stops after the first transfer.

**What stopped it.** TI's code lays structs and a 32-bit bit-field union over the SPI buffer, and a C28x struct member takes a whole 16-bit word. A header file cannot change that. Also, 29 shifts of `1 << 16` and up overflow a 16-bit `int`.

**Next.** Write a packer (`pack_TRX_Request_*` and the header) that fills a byte-per-word buffer field by field, run it against the same PC reference bytes, then try a real BP-CC1407P.

**Board state.** RAM load only. Flash read before and after: SHA-256 identical to the as-received image; the board was reset into TI's demo.
